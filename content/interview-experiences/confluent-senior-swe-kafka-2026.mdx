// Feature engineering - transaction velocity per account
KTable<String, TransactionStats> accountStats = transactions
    .groupByKey()

    .aggregate(

        (key, transaction, stats) -> stats.addTransaction(transaction),
        Materialized.<String, TransactionStats, WindowStore<Bytes, byte[]>>as("account-stats-store")

    .leftJoin(accountStats,

        Joined.with(Serdes.String(), transactionSerde, statsSerde))
    .filter((key, evaluation) -> evaluation.isFraudulent())

public class FraudEvaluator {
    
    public FraudEvaluation evaluateForFraud(Transaction txn, TransactionStats stats) {
        List<FraudSignal> signals = new ArrayList<>();
        
        // Velocity-based detection
        if (stats != null && stats.getTransactionCount() > 10) {
            signals.add(FraudSignal.HIGH_VELOCITY);
        }
        
        // Amount-based anomaly detection
        if (txn.getAmount() > stats.getAverageAmount() * 5) {

        // Time-based patterns
        if (isUnusualTimePattern(txn, stats.getHistoricalTimes())) {
            signals.add(FraudSignal.TIME_ANOMALY);
        }
        
        return new FraudEvaluation(txn.getTransactionId(), signals,

    }
}

## Virtual Onsite Loop (4 Rounds)

### Round 3: Kafka Internals Deep-Dive (1.5 hours)

**The most critical round** - testing deep understanding of Apache Kafka internals.

#### Part 1: Producer Internals and Optimization (45 minutes)

**Question**: "Explain what happens when a producer sends a message to Kafka, from client to disk persistence."

**My Detailed Explanation**:

1. **Client-Side Processing**:
   - Message serialization using configured serializers
   - Partitioner determines target partition (key-based, round-robin, or custom)
   - Message added to RecordAccumulator buffer organized by topic-partition
   - Batching occurs based on `linger.ms` and `batch.size` configuration

2. **Network Layer**:
   - NetworkClient sends batched requests to appropriate broker leaders
   - TCP connection management with connection pooling
   - Request pipelining for throughput optimization

3. **Broker-Side Processing**:
   - Request processing by network threads (acceptor + processor threads)
   - Validation: partition exists, client has write permissions, message size limits
   - Log appending by IO threads to partition's log segments

4. **Disk Persistence**:
   - Write to OS page cache (not immediately fsynced for performance)
   - Log segment rolling based on size/time thresholds
   - Index updates (offset index, timestamp index, transaction index)

**Follow-up Questions**:

**Q: How does `acks=all` affect this flow?**
**A**: Producer waits for all in-sync replicas (ISR) to acknowledge. Broker leader waits for followers to fetch and acknowledge before responding to producer. Increases latency but provides strongest durability guarantee.

**Q: What happens if a broker fails during message production?**
**A**: 
- If leader fails: Controller elects new leader from ISR, producer retries to new leader
- If follower fails: Removed from ISR, production continues with remaining replicas
- Producer-side retries with exponential backoff handle transient failures

#### Part 2: Consumer Group Internals (45 minutes)

**Question**: "Walk me through the consumer group rebalancing process and its implications."

**My Explanation**:

1. **Group Coordination**:
   - Group coordinator selection based on `__consumer_offsets` partition hash
   - Heartbeat mechanism for liveness detection (`session.timeout.ms`)
   - JoinGroup and SyncGroup protocols for membership management

2. **Rebalancing Triggers**:
   - New consumer joins the group
   - Consumer leaves (graceful or timeout-based)
   - Partition count changes (topic scaling)
   - Consumer subscription changes

3. **Rebalancing Protocol**:
   ```
   Consumer -> JoinGroup Request -> Group Coordinator
   Group Coordinator -> Partition Assignment -> Group Leader Consumer
   Group Leader -> SyncGroup (Assignment) -> Group Coordinator
   Group Coordinator -> SyncGroup Response -> All Consumers
   ```

4. **Partition Assignment Strategies**:
   - **Range**: Assigns consecutive partitions (can cause imbalance)
   - **RoundRobin**: Evenly distributes partitions (requires same subscription)
   - **Sticky**: Minimizes partition movement during rebalance
   - **Cooperative Sticky**: Allows incremental rebalancing without stopping consumption

**Performance Implications Discussion**:
- Stop-the-world rebalancing vs incremental rebalancing
- Impact on end-to-end latency during rebalance
- Strategies for minimizing rebalance frequency

### Round 5: Streaming Systems Design Challenge (1 hour)

**Problem**: Design a real-time recommendation system for an e-commerce platform using Kafka Streams.

**Requirements**:
- Process 100K user interaction events per second
- Generate personalized recommendations within 50ms
- Handle cold start problem for new users
- Support A/B testing for recommendation algorithms

**My Kafka Streams Solution**:

```java
@Component
public class RecommendationTopology {
    
    public Topology buildTopology() {
        StreamsBuilder builder = new StreamsBuilder();
        
        // User interaction events
        KStream<String, UserInteraction> interactions = builder.stream("user-interactions");
        
        // Product catalog as KTable
        KTable<String, Product> products = builder.table("product-catalog");
        
        // User profiles with preferences
        KTable<String, UserProfile> userProfiles = builder.table("user-profiles");
        
        // Real-time feature engineering
        KStream<String, UserFeatures> features = interactions
            .groupByKey()
            .windowedBy(TimeWindows.of(Duration.ofMinutes(30)))
            .aggregate(
                UserFeatures::new,
                (key, interaction, features) -> features.addInteraction(interaction),
                Materialized.as("user-features-store")
            )
            .toStream()
            .map((windowedKey, features) -> KeyValue.pair(windowedKey.key(), features));
        
        // Join features with user profile for recommendation generation
        KStream<String, Recommendation> recommendations = features
            .leftJoin(userProfiles, this::generateRecommendations)
            .filter((key, rec) -> rec != null);
        
        // A/B testing split
        KStream<String, Recommendation>[] testingBranches = recommendations.branch(
            (key, rec) -> rec.getUserId().hashCode() % 100 < 50,  // 50% to variant A
            (key, rec) -> true  // 50% to variant B
        );
        
        // Different algorithms for A/B testing
        testingBranches[0]
            .mapValues(rec -> applyAlgorithmA(rec))
            .to("recommendations-variant-a");
            
        testingBranches[1]
            .mapValues(rec -> applyAlgorithmB(rec))
            .to("recommendations-variant-b");
        
        return builder.build();
    }
    
    private Recommendation generateRecommendations(UserFeatures features, UserProfile profile) {
        // Cold start handling
        if (profile == null || features.getInteractionCount() < 5) {
            return generateColdStartRecommendations(features);
        }
        
        // Collaborative filtering + content-based hybrid approach
        List<String> recommendations = new ArrayList<>();
        
        // Recent category preferences
        Map<String, Double> categoryScores = features.getCategoryPreferences();
        
        // Similar user patterns (would be pre-computed in reality)
        List<String> similarUserPreferences = profile.getSimilarUserPreferences();
        
        // Combine signals
        recommendations.addAll(getTopProductsByCategory(categoryScores));
        recommendations.addAll(similarUserPreferences.subList(0, 
            Math.min(5, similarUserPreferences.size())));
        
        return new Recommendation(profile.getUserId(), recommendations, "hybrid");
    }
}
```

**Key Design Decisions**:
- **Windowed Aggregations**: Capture recent user behavior patterns
- **KTable Joins**: Enrich streams with relatively static profile data  
- **Branching**: A/B testing implementation at stream processing level
- **State Stores**: Local caching of user features for low-latency access

**Confluent-Specific Features**:
- Exactly-once processing for consistent recommendation generation
- Interactive queries for serving real-time user features to web services
- Schema Registry for evolution of recommendation algorithms
