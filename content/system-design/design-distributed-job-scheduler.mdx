A single-machine cron is trivial. **Cron at scale**, the platform that fires off "send daily digest at 8 AM," "rebuild search index every hour," "expire trial accounts at 90 days," "run this Spark job after that one finishes", is one of the more interesting distributed systems problems. The hard parts: **exactly-once execution**, **failure recovery**, and **dependency graphs (DAGs)**.

## 1. Clarify before you draw

- **Recurring (cron) jobs, one-off jobs, or both?**
- **Latency tolerance?** Must fire within 1 second of scheduled time, or within 1 minute?
- **Exactly-once or at-least-once execution?**
- **DAG support?** (Job A finishes → trigger Job B + Job C → trigger Job D when both done.)
- **Job duration?** Microseconds to hours?
- **Volume?** 10K jobs/day, or 10M?

For this post: full platform, cron + one-off + DAGs, ~10M jobs/day, exactly-once execution, ~1-min granularity, jobs can run from milliseconds to many hours.

## 2. Functional & non-functional requirements

**Functional:**
1. Schedule a one-off job for a future time.
2. Schedule a recurring (cron) job.
3. Define DAGs (jobs depending on other jobs).
4. Trigger jobs exactly once at the scheduled time.
5. Track status, retry on failure, surface logs.

**Non-functional:**
1. **High availability**, scheduler outage = missed runs = real damage.
2. **Exactly-once execution**, no double-runs.
3. **Bounded latency** between scheduled and actual fire time.
4. **Scale to 10M+ jobs/day**.

## 3. Capacity numbers

- 10M jobs/day → **~120 jobs/sec average**, ~5K peak (jobs cluster on top of the hour).
- Storing 1 yr of job history at 1 KB each = **~3.6 TB** queryable history.
- Worker fleet: depends entirely on per-job duration, but the **scheduler** (firing logic) is small, single-digit nodes.

## 4. The two-layer architecture

```
┌────────────────────────────────────┐
│  SCHEDULER LAYER                   │
│  - Stores job definitions          │
│  - Decides "what runs when"        │
│  - Pushes jobs to execution queue  │
└──────────────┬─────────────────────┘
               │
               ▼
┌────────────────────────────────────┐
│  EXECUTION LAYER                   │
│  - Worker pool consumes queue      │
│  - Runs jobs (Docker / K8s / FaaS) │
│  - Reports status back             │
└────────────────────────────────────┘
```

Critical separation: **scheduling correctness** (don't drop or double-run a job) lives in the scheduler. **Execution scale** (run 10K Docker containers/sec) lives in the execution layer. Scaling them independently keeps each tractable.

## 5. The "what should run now?" problem

Naive: "every minute, scan all jobs WHERE next_run_at &lt; now()." At 10M scheduled jobs, that's a full table scan every minute. Doesn't scale.

### Time-bucketed index

Bucket jobs by minute of next run:

```sql
CREATE TABLE scheduled_jobs (
  job_id      bigint  PK,
  next_run_at timestamp,
  bucket      bigint generated as (extract(epoch from next_run_at)::bigint / 60),
  ...
);
CREATE INDEX ON scheduled_jobs(bucket);
```

Every minute, the scheduler reads jobs with `bucket = current_minute_bucket`. Cheap range scan. After firing, the job's `next_run_at` is recomputed (for cron jobs) and the index updates accordingly.

### Sharded scheduler

Hash jobs by `job_id % N` to N scheduler shards. Each shard owns its slice of jobs. Allows horizontal scale of the firing logic.

```
Shard 0: jobs whose hash % 4 == 0
Shard 1: jobs whose hash % 4 == 1
...
```

A leader-elected process per shard scans its time bucket every minute. Leader election via a [distributed locking service](/blog/system-design/design-distributed-locking-service).

## 6. Exactly-once execution (the hardest requirement)

"Exactly-once" is impossible in a strict sense, but the right combination achieves "exactly-once observable effect."

### The lease + fencing token pattern

```
1. Scheduler decides Job J should run at T.
2. Insert an "execution attempt" row:
     INSERT INTO job_runs (run_id, job_id, scheduled_at, status='QUEUED')
3. Push to execution queue with a fencing_token = run_id.
4. Worker pulls from queue:
     - Try to acquire a lease on job_id with fencing_token.
     - If another worker already holds the lease → drop this attempt.
     - Else: execute job, write result keyed by run_id.
5. Worker reports completion: UPDATE job_runs SET status='SUCCESS' WHERE run_id=...
```

The **fencing token** prevents the classic "old worker wakes up after a long pause and tries to write" bug. Downstream systems reject any write with a token older than the latest one they've seen.

### Idempotency in the job itself

Even with fencing, the job code should be **idempotent**. If "send email to user X" runs twice somehow, the user shouldn't get two emails. Use the `run_id` as a dedup token in any external API calls, same trick as in the [Payment System](/blog/system-design/design-payment-system#4-the-non-negotiable-idempotency-on-every-api).

## 7. Cron jobs (recurring)

A cron job is a job whose `next_run_at` is recomputed on completion:

```python
def on_complete(job, result):
    if job.is_cron:
        job.next_run_at = compute_next_fire(job.cron_expression, now())
        save(job)
```

Don't recompute the next run from `now()` if you want strict cadence, recompute from the *scheduled* time so missed minutes don't pile up. Optionally add a "catchup window" parameter so a job that missed last hour doesn't fire 60 times now.

## 8. DAG support (depends-on)

A DAG of jobs: Job A → Job B → Job C, where B starts only after A succeeds.

Schema:
```sql
job_definitions(job_id, ...)
job_dependencies(job_id, depends_on_job_id)
job_runs(run_id, job_id, status, started_at, finished_at)
```

Execution:
```
1. When a job completes, fire an event "job_X_finished".
2. Dispatcher consumes the event, queries jobs with depends_on=X.
3. For each dependent: check if ALL its dependencies are now SUCCESS for the relevant logical date.
4. If yes: schedule it.
```

This is exactly how Apache Airflow, Prefect, and Argo Workflows operate. Mention them by name.

For very large DAGs (1000+ tasks), the dispatcher uses a per-DAG state machine in memory; full DAG state is also persisted for crash recovery.

## 9. Job execution layer

Once a job is queued, it needs to actually run. Options:

| Approach | When |
|---|---|
| **Persistent worker pool** | Many small jobs; low launch latency required |
| **Container-per-job** (Docker, K8s Jobs) | Heterogeneous environments; isolation needed |
| **FaaS** (Lambda, Cloud Run) | Bursty, sub-15-min jobs; pay-per-use is cheap |
| **Submit to external compute** (Spark, Dataflow) | Heavy data jobs; defer to specialized infra |

A real platform supports multiple. The scheduler doesn't care how the job runs; it just dispatches and listens for completion.

## 10. Failure handling

| Failure | Behavior |
|---|---|
| **Worker crashes mid-job** | Lease expires (no heartbeat); another worker picks up; idempotency in the job handles re-execution |
| **Scheduler shard's leader dies** | Distributed lock service triggers re-election; new leader resumes from current bucket |
| **Job fails (exit code != 0)** | Retry with backoff up to N times; then mark FAILED + alert |
| **Downstream queue down** | Jobs queue locally on scheduler; flush on recovery |
| **Time goes backwards (NTP step)** | Time-bucketed index handles it (jobs re-fire from older bucket); lease + idempotency prevents double-effect |

## 11. Observability

Every fire path needs:
- Per-job: last N runs (status, duration, logs link).
- Per-shard: queue depth, scheduler lag (now − latest fired bucket), leader status.
- Alerts on: missed runs (no fire within X seconds of scheduled time), high failure rate, lease expirations.

## 12. The trade-offs interviewers will probe

| Question | What they want to hear |
|---|---|
| "How do you do exactly-once?" | Lease + fencing token + idempotent job code |
| "How do you scan 10M jobs efficiently?" | Time-bucketed index + sharded scheduler |
| "What if the scheduler dies right at the fire time?" | Leader re-election; new leader resumes the bucket |
| "How do you handle DAG fan-in (job D depends on B and C)?" | Event-driven dispatcher checks all deps satisfied |
| "Can a cron job miss a window?" | Catchup option vs strict cadence; configurable per job |
| "Why not just use Kubernetes CronJobs?" | Fine for &lt;1000 jobs; no DAGs, no shared platform observability |
| "How do you handle long-running jobs?" | Lease heartbeat + eviction on missed heartbeat |

## 13. The 30-second summary

> A distributed scheduler is a **time-bucketed index + sharded leader-elected dispatchers + exactly-once execution via leases and fencing tokens**. The scheduler decides "what runs when"; the execution layer (containers, workers, FaaS) actually runs it. DAGs are state machines driven by completion events. Failure recovery is designed in via leases that expire on crashed workers. The whole system is operationally tractable because scheduling and execution are scaled independently.

Land that with the lease + fencing token pattern from section 6, and you've answered the staff version.
