"Design Google Maps" is one of the broadest system design questions you'll see. It contains at least four sub-systems: a **map rendering / tile delivery pipeline**, a **geocoding service**, a **routing engine** with sub-second latency on planet-scale graphs, and a **real-time traffic layer** that reshapes routes in real time. Junior candidates pick one and spend 45 minutes there; staff candidates sketch all four in the right depth.

## 1. Clarify before you draw

- **Scope?** Just maps display, or routing + traffic + Street View + indoor + AR?
- **Routing modes?** Driving, transit, walking, biking?
- **Real-time traffic?** Yes (the interesting design choice).
- **Geographic coverage?** Whole world, or just one country?

For this post: world-scale maps + driving routing + real-time traffic + geocoding. ~1B MAU, ~1B route queries/day.

## 2. Capacity numbers

- World map at zoom levels 0–22 → ~22 trillion possible 256×256 tiles. Most are empty (oceans). Real number ≈ ~50B distinct rendered tiles.
- Tile data total ≈ 100 TB compressed.
- 1B route queries/day → ~12K queries/sec average, ~100K peak.
- 100M+ active drivers anonymously contributing speed probes → ~1M location updates/sec aggregated.

The numbers tell you: tiles are CDN-static; routing is compute-heavy and personalized.

## 3. Architecture overview

```
                                ┌─► Tile Service ──► CDN
Mobile / Web ─► API Gateway ────┤
                                ├─► Geocoding Service
                                ├─► Routing Service ─► Map Graph DB
                                └─► Traffic Service  ─► Probe Aggregation Pipeline
```

Each is its own subsystem with its own scaling. The unifying glue is a **shared map graph** (nodes = intersections, edges = road segments) used by routing, geocoding, and traffic.

## 4. The tile pyramid (map display)

Maps are served as a **pyramid of pre-rendered tiles**:

```
Zoom 0:   1 tile   covers the entire world
Zoom 1:   4 tiles  (each is a quarter)
Zoom 2:  16 tiles
...
Zoom 18: 70B tiles (street level)
Zoom 22: trillions
```

Each tile is a 256×256 image (PNG / WebP) or a vector tile (Mapbox/Google use vectors now, smaller, themable, sharper on retina). URL pattern:

```
https://tiles.example/<z>/<x>/<y>.pbf
```

Where `(x, y)` are tile coords at zoom `z`. Pure static asset → CDN-cacheable forever. When map data updates (a new road), you bump the tile's version (different URL), preserving cache integrity.

### Why vector tiles, not raster

- 5–10× smaller download.
- Re-renderable client-side at any rotation, theme, or label density.
- Smooth zoom + animation.
- Mobile-friendly (data plans).

Real maps APIs ship raster as a fallback for old clients, vector for everyone else.

## 5. The map graph (heart of routing)

The road network is a **directed weighted graph**:
- **Nodes:** intersections (lat, lng).
- **Edges:** road segments between intersections, with weights (length × travel time × turn cost).
- **Edge attributes:** speed limit, road type (highway / residential / etc.), one-way, restrictions.

For the world: ~10⁹ nodes, ~3×10⁹ edges. Stored in a custom on-disk format with spatial partitioning (one file per geographic region, mmap'd).

## 6. Routing, why naive Dijkstra/A\* doesn't fly

Naive A\* on a 10⁹-node graph for an LA-to-NYC route → seconds to minutes. Need **&lt;1 second**.

Two big preprocessing wins (do them once, query fast forever):

### A. Contraction Hierarchies (CH)
Precompute a hierarchy where "important" roads (highways) are contracted. Bidirectional Dijkstra running on the contracted graph is **~1000× faster** than on the full graph. Used by OSRM and many routing engines.

### B. Hub Labeling / ALT (A\*, Landmarks, Triangle inequality)
Pre-pick ~20 "landmarks" globally and store distance from every node to each landmark. A\* heuristic uses landmark distances → much tighter, much faster than Euclidean heuristic.

Combine both: cross-country queries return in **~10–50 ms**.

### Multiple modes & preferences
Each mode (driving / walking / biking / transit) is a different graph (different edge weights, different valid edges). Maintain ~4 graphs. Real-time traffic adjusts the *driving* graph's edge weights every minute.

## 7. Real-time traffic (the design's most interesting layer)

Where does Google get its traffic data? **From you.** Every Android phone with location services pings anonymized location to Google. Aggregating these gives a real-time map of speeds on every road segment.

Pipeline:
```
Phone GPS pings (1M+/sec)
       │
       ▼
Anonymization layer
       │
       ▼
Map-matching: snap each ping to a road segment
       │
       ▼
Per-segment speed aggregation (Flink / Beam, 1-min windows)
       │
       ▼
Road-segment speed table (Redis / KV, ~1 min freshness)
       │
       ▼
Routing service reads this when computing edge weights
```

When traffic on a segment slows, that segment's edge weight increases → A\* re-routes around it. **All in roughly 1 minute end-to-end.**

Privacy notes (mention briefly): pings are anonymized by stripping device IDs and bucketing locations into coarse cells before aggregation. Individual users can't be re-identified from the aggregate.

## 8. Geocoding, "near me" queries

Two flavors:
- **Forward geocoding:** "1600 Amphitheatre Parkway" → `(lat, lng)`.
- **Reverse geocoding:** `(lat, lng)` → "1600 Amphitheatre Parkway."

Backed by:
- A **places index** (every named place: businesses, addresses, landmarks).
- An **address-to-location lookup table** (street + number → coords).
- A **search index** (Elasticsearch / Vespa) over place names + addresses.

Queries fuzzy-match (typos, abbreviations) and rank by popularity + proximity to the user.

For "coffee shop near me": query the places index with category=`coffee` and a geospatial filter (S2 cells around user). Cross-link to [Design Uber](/blog/system-design/design-uber-ride-sharing#4-geospatial-indexing-pick-exactly-one-scheme) for the geospatial primitives.

## 9. Address suggestions / autocomplete

Same machinery as [Search Autocomplete (Typeahead)](/blog/system-design/design-typeahead-autocomplete), but with personalization (your home address ranks first; nearby addresses rank above far ones).

## 10. ETA computation

When a user starts navigating, Maps shows an ETA that updates as they drive:

```
ETA(t) = sum of edge_weights along remaining path,
         where edge_weights use real-time traffic.
```

Re-computed every ~30 seconds during navigation. If a faster alternative emerges (you're stuck in traffic, an off-ramp would save 10 min), surface a "faster route" suggestion.

## 11. Street-level imagery (Street View), separate system

Out of scope for the headline question, but worth knowing: Street View is a separate object-storage + tile pyramid for the imagery, plus a depth model for 3D rendering. Mention it exists if asked.

## 12. Failure handling

| Failure | Behavior |
|---|---|
| **Tile CDN miss spike** | Origin returns the tile; result cached at edge for next viewer |
| **Routing service down** | Mobile clients can route on a small offline graph (pre-downloaded city) |
| **Traffic pipeline down** | Falls back to historical traffic (time-of-day average) |
| **Geocoding down** | Search shows no results; map still renders |

Famous Maps lesson: **offline-first** for the mobile app. Users in areas with poor connectivity (most of the world) need maps + routing to work without network.

## 13. The trade-offs interviewers will probe

| Question | What they want to hear |
|---|---|
| "Why pre-rendered tiles, not on-the-fly?" | CDN cacheability at scale |
| "Why vector tiles?" | Smaller, re-renderable, smooth zoom |
| "Why not naive Dijkstra for routing?" | Way too slow at planet scale; CH + ALT preprocessing |
| "Where does real-time traffic come from?" | Anonymized phone GPS pings → Flink → per-segment speeds |
| "How do you serve 1B users globally with low latency?" | Tile CDN, regional routing services, mobile offline maps |
| "Why separate driving/walking/transit?" | Different graphs (different valid edges, different weights) |
| "How do you keep the map current?" | Crowdsourced edits (Map Maker / Map Editor); satellite imagery review; bulk vendor data |

## 14. The 30-second summary

> Google Maps is **four subsystems**: a tile pyramid CDN-served as static assets, a planet-scale routing engine using contraction hierarchies + ALT preprocessing for sub-second queries, a real-time traffic layer fed by anonymized phone GPS pings stream-aggregated per road segment, and a geocoding service backed by a search index over places. The unifying primitive is the road graph; everything else is layered on top.

Land that with the routing-preprocessing math (Dijkstra → CH → ~1000× speedup) from section 6, and you've answered the staff version.
