"Design WhatsApp" looks like a UI question and is actually a deep distributed-systems question wearing a casual shirt. The hard parts: **long-lived connections at scale**, **strict per-conversation ordering**, **presence at billions-of-users scale**, and **offline message delivery**. Junior candidates draw a chat box; staff candidates spend 30 minutes on the connection layer.

## 1. Clarify before you draw

- **1:1 chat only, or groups too?** Groups change the fan-out story.
- **Group size cap?** 100? 1,000? 256K (WhatsApp Communities)?
- **Read receipts and typing indicators?**
- **Online presence?** (Last seen vs always-current)
- **Media (images, video, voice notes)?**
- **End-to-end encryption?** (Yes for WhatsApp; usually out of scope for the design *itself*.)
- **Message history persisted?** (Yes for WhatsApp on user-pulled backups; ephemeral for Snapchat-style)

For this post: 1:1 + groups up to 1,000, read receipts, presence, persistent history, ~3B users, ~100B messages/day.

## 2. Functional & non-functional requirements

**Functional:**
1. Send / receive messages (text + media references).
2. Group chat (up to 1K members).
3. Online presence + last-seen.
4. Delivery receipts (sent, delivered, read).
5. Offline message delivery (queue messages until recipient comes online).
6. Message history.

**Non-functional:**
1. **Per-conversation ordering** — messages arrive in send order.
2. **Low send-to-deliver latency** — p99 &lt; 500 ms when recipient is online.
3. **High availability** — 99.99% for the messaging path.
4. **Durability** — never lose a sent message.
5. **Scale to 3B concurrent connections globally**.

## 3. Capacity numbers

- 3B users × ~70% online during peak = **~2B concurrent connections**.
- At ~10 KB memory per WebSocket → ~20 PB RAM. Spread across **~100K connection servers** at 50K connections each.
- 100B messages/day → **~1.2M msgs/sec average, ~10M peak**.
- Average message ~500 bytes → **5 GB/s ingress**, 5 GB/s egress (1:1 fanout).
- Storage: 100B × 365 × 5 yrs × 500 B = **~90 PB** (with replication, ~270 PB). Compressed ~100 PB.

## 4. The two foundational components

```
Client ────────WebSocket────────► Connection Server ───► Message Service ───► Storage
  (long-lived TCP, ~hours)         (stateful, holds          (stateless,         (Cassandra,
                                    50K conns each)           message logic)      partitioned by
                                                                                  conversation_id)
```

The **connection server** is the most important and least-talked-about piece. It owns the long-lived TCP socket. Everything else is roughly stateless and easy.

## 5. Connection layer: the part candidates skip

A staff-level answer dwells here for 5+ minutes.

### Why WebSockets, not polling

Polling at 100ms intervals across 2B clients = 20B requests/sec. Untenable. WebSockets give you a single TCP connection per client, kept open for hours, with sub-second message delivery and ~10× less server CPU.

Trade-off: stateful servers. A connection server **owns** specific users; if it dies, those users reconnect (and might land on a different server). The system needs to know "user U is on server S" to route messages.

### Routing layer (the user → server map)

A **session registry** (Redis, or sharded by user_id) holds:

```
user_id → { connection_server_id, session_token, last_heartbeat }
```

When server X wants to send a message to user Y:
1. Look up Y in the session registry → get server S.
2. Send message to S via internal RPC.
3. S finds Y's local socket and pushes the frame.

If Y isn't online, the message goes to Y's offline queue (section 9).

### Connection server sharding

By user_id hash, with consistent hashing (see [Distributed Cache](/blog/system-design/design-distributed-cache#5-partitioning-consistent-hashing-is-non-negotiable)). Adding/removing connection servers reshuffles ~1/N of users — they reconnect within seconds.

## 6. Message send path

```
1. User A's app emits SendMessage(conversation_id, text) over its WebSocket.
2. Connection server receives, forwards to Message Service.
3. Message Service:
   a. Generates message_id (Snowflake — see the URL Shortener post for the anatomy).
   b. Persists to messages table (sharded by conversation_id, sorted by message_id).
   c. For each recipient in the conversation:
      - Look up their connection in session registry.
      - If online: forward to their connection server, which pushes to socket.
      - If offline: write to their offline queue (Kafka topic per shard, or Cassandra).
   d. Returns ack to A's connection server with message_id + server_timestamp.
4. A sees a "✓ sent" tick.
```

End-to-end latency for two online users: typically ~50–200 ms.

## 7. Per-conversation ordering — the trickiest part

Total ordering across the whole system is impossible at this scale. You need ordering **within a single conversation only**.

The trick: **shard messages by `conversation_id`**, route all writes for the same conversation to the same shard, and use a single sequence per conversation. That sequence becomes the canonical order; clients sort by it.

```sql
CREATE TABLE messages (
  conversation_id  bigint,
  seq              bigint,           -- monotonic per conversation
  sender_id        bigint,
  message_id       bigint,           -- Snowflake (globally unique)
  content          blob,
  created_at       timestamp,
  PRIMARY KEY (conversation_id, seq)
);
```

Two senders in the same conversation hit the same shard, get serialized via a per-conversation lock or single-writer-per-shard pattern. Two senders in *different* conversations are fully parallel.

## 8. Group chat fan-out

For 1,000-member groups, you have two options (just like [News Feed](/blog/system-design/design-news-feed-twitter)):

| Approach | When |
|---|---|
| **Push to every member's offline queue + push to online sockets** | Default. Cheap at 1K members. |
| **Pull at read time** (members fetch from group log) | Required for huge groups (10K+ members, "communities" / channels). |

WhatsApp uses fan-out-on-write up to ~256K members in Communities by *batching* the writes — one Kafka message per group post that downstream workers expand into per-recipient writes. A single group post still fans out to 256K rows; the work is just async.

## 9. Offline queue

Each user has a per-user "inbox" of messages they haven't received yet:

- Stored in Cassandra (or a dedicated "mailbox" service backed by a log-structured store).
- When user reconnects, the connection server pulls all queued messages, ack'd in batches.
- After client ack, messages are removed from the inbox (or marked delivered).
- TTL of ~30 days on undelivered messages (configurable).

For very large queues (long-offline users), pagination is mandatory — don't try to push 50K messages over a fresh socket in one frame.

## 10. Presence (the hidden monster)

Naive presence: every client publishes a heartbeat every 30 s. With 2B clients = **~70M req/sec just for heartbeats**. Brutal.

Smarter approach:

- **Connection presence is implicit** — if the WebSocket is connected, the user is "online." No extra heartbeat needed at the application layer; TCP keep-alive (every 60–120 s) does the job.
- **Last-seen** is updated on disconnect, not periodically.
- **Presence updates fan out only to "interested" parties** — your contacts, group members you're chatting with right now. Not the whole graph.
- For "is X online?" lookups: cache in Redis with a 30s TTL, derived from the session registry.

WhatsApp went one step further: it shows last-seen *only* to chats you've actually messaged — drastically cutting the fan-out.

## 11. Read receipts and typing indicators

Both are just **lightweight messages** on the same connection layer:

- `typing_start` / `typing_stop` — ephemeral, not persisted, only forwarded to currently-online conversation participants.
- `delivery_receipt` — when client receives a message, it sends back a tiny ack frame; written to the message row's `delivered_at`. Echoed to sender.
- `read_receipt` — when client renders the message on screen, sends back another ack; updates `read_at`. Echoed.

Don't persist typing indicators. They're noise within seconds.

## 12. End-to-end encryption (mention but don't go deep)

WhatsApp uses the Signal Protocol: each pair of users has a Double Ratchet of keys; messages are encrypted client-to-client; **the server never sees plaintext**.

Implications for the design:
- Server can't read or index message content.
- Search and full-text features are client-side only.
- Backups are encrypted with a user-held key (or written to client's iCloud/Drive in plaintext, depending on settings).
- Group encryption uses Sender Keys — each member maintains a key per group; new joiners trigger a key refresh.

In an interview, **mention E2E exists and skip the crypto deep-dive** unless asked. Show that you know it constrains the design.

## 13. Failure handling

| Failure | Behavior |
|---|---|
| **Connection server crashes** | All its sockets drop. Clients auto-reconnect via load balancer; session registry updated on new login. |
| **Message Service crashes mid-send** | If write to messages table succeeded, ack flows. If not, sender retries with same idempotency key (`client_msg_id`). |
| **Recipient flaky** | Repeated push retries with backoff; eventually goes to offline queue. |
| **Network partition** | Senders see "sending..." stuck; messages queue locally and replay on reconnect. |

Idempotency is critical: clients send a `client_msg_id` (UUID) with every message. Server dedups: if the same `client_msg_id` arrives twice, return the same `message_id` — don't double-store.

## 14. The trade-offs interviewers will probe

| Question | What they want to hear |
|---|---|
| "Why WebSockets, not long polling?" | Cost at this scale; sub-second latency |
| "How do you maintain per-conversation order?" | Single shard per conversation, sequence number |
| "What about ordering across conversations?" | Doesn't matter; clients sort per-conversation |
| "How do you handle a 1M-member group?" | Lazy fan-out + pull at read; channel semantics |
| "What if the connection server holding 50K users dies?" | Reconnect to a different one; session registry updates; offline messages drained on reconnect |
| "How do you scale presence?" | Implicit (TCP-based); fan out only to interested parties |
| "How do you ensure exactly-once message delivery?" | Client `idempotency_key` + server dedup; clients dedup by `message_id` on render |

## 15. The 30-second summary

> A chat system is fundamentally a **fleet of stateful WebSocket servers behind a session registry, feeding messages into a per-conversation sharded log, with offline queues for the not-currently-connected**. The hard parts are connection scale (millions per box), per-conversation ordering, and presence without melting the heartbeat layer. End-to-end encryption is a constraint, not a feature. Group fan-out reuses News Feed's hybrid push/pull pattern.

Land that summary plus the connection-layer depth from section 5, and you've answered the question at a staff bar.
