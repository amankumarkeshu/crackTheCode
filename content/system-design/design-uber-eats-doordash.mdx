Uber Eats / DoorDash / Swiggy / Zomato are all **three-sided marketplaces**: customer wants food, restaurant cooks, courier delivers. Each side has its own data, latency, and incentive constraints. Designing this is meaningfully different from designing rides — the ETA isn't just driving time, the catalog is huge and changes every hour, and you have a literal hot meal that goes cold while you optimize.

## 1. Clarify before you draw

- **Geographic scope?** Single city / national / global?
- **Delivery model?** Marketplace (we connect; they deliver themselves), platform (we provide couriers), or both?
- **Couriers?** Gig workers who pick up multiple orders, or dedicated per-restaurant?
- **Order volume?** ~2M/day (Indian metro) or ~10M/day (DoorDash US)?
- **Batched deliveries?** Pick up multiple orders at the same restaurant on one route?

For this post: platform with gig couriers, ~10M orders/day across thousands of cities, batching and surge built in.

## 2. Functional & non-functional requirements

**Functional:**
1. Customer browses restaurants → sees menu → places order → tracks delivery.
2. Restaurant receives order → confirms → cooks → marks ready.
3. Courier gets matched → drives to restaurant → picks up → delivers.
4. Catalog (menus, prices, hours, availability) stays current.
5. Payments to restaurants and couriers settle daily/weekly.

**Non-functional:**
1. **Real-time location** for tracking.
2. **Reliability** — orders can't go missing.
3. **Fast matching** — courier assigned within seconds.
4. **Accurate ETAs** — customer trust depends on this.
5. **Three-sided fairness** — pricing and incentives must work for all sides.

## 3. Capacity numbers

- 10M orders/day = ~115 orders/sec avg, ~500/sec peak (lunch/dinner).
- ~500K active couriers globally; ~5M restaurants.
- Catalog: ~5M restaurants × ~100 items avg = **500M menu items**. Updated frequently (price changes, sold out, hours).
- Real-time tracking: ~500K courier location pings/sec at peak = same scale as [Uber](/blog/system-design/design-uber-ride-sharing).

## 5. The catalog: bigger problem than you'd think

A 500M-item catalog where prices change at lunch, items sell out mid-shift, hours shift on holidays, and a wrong menu = unhappy customer + angry restaurant.

**Catalog architecture:**
- **Source of truth:** restaurant profile in a relational DB.
- **Read replicas / cache:** Redis/Memcached for hot catalog reads.
- **Search index:** Elasticsearch — restaurants searchable by name, cuisine, location.
- **Personalized "for you":** ranked recommendations from a separate ML service.

### Real-time updates
A restaurant marking an item sold out should propagate to all customers in &lt;5 sec.
- Restaurant tablet → Catalog Service → Redis cache update + Kafka event.
- Customer apps subscribed via WebSocket / long-poll → push update.
- For customers already viewing the restaurant: refresh menu when they tap "checkout."

### Hours & availability
Restaurants set hours per day. Plus geo-fenced delivery: only show restaurants within X km / Y minutes drive.
- Geospatial query at search time: `restaurants WHERE geo_within(user_lat, user_lng, 5km) AND open_now()`.
- Use Geohash / S2 cells for indexing (same as [Uber](/blog/system-design/design-uber-ride-sharing)).

## 6. The order state machine

```
   placed
      │ payment authorized
      ▼
  payment_captured
      │ restaurant accepts
      ▼
  restaurant_accepted
      │ matching finds courier
      ▼
  courier_assigned
      │ restaurant marks ready
      ▼
  ready_for_pickup
      │ courier picks up
      ▼
  in_transit
      │ courier delivers
      ▼
   delivered
      │
      ▼
   settled (T+1 day)

  Branches:
   - cancelled (customer, restaurant, or system)
   - refunded (post-delivery issue)
   - failed (couldn't find courier in time)
```

State stored in a relational DB (Postgres, MySQL — orders are firmly transactional). Each state transition is **idempotent** with version checking — same as [Uber](/blog/system-design/design-uber-ride-sharing).

Events emitted to Kafka so other services react:
- Matching service triggers on `restaurant_accepted`.
- ETA service updates on every state change.
- Customer notification service pushes "Your order is on its way!" on `in_transit`.

## 7. Courier matching: smarter than "nearest"

For rides, "nearest available driver" is usually right. For food delivery, it's wrong:
- The food isn't ready yet — assign too early and the courier waits, hating you.
- Other orders might come in 30 sec later that batch with this one.
- Some couriers prefer cars vs bikes; some don't go to certain areas.

### The matching algorithm

```
Inputs:
  - Pending orders with predicted ready times
  - Available couriers with current locations + capacities (single/batch)
  - Restaurants' geo + cooking time predictions

Solve (every ~5 sec):
  - Assign couriers to orders to minimize: ∑ delay + fuel + couriers used
  - Subject to: each courier delivers ≤ K orders, each delivered within SLA
  
This is a constrained optimization (mini "vehicle routing problem").
```

In practice, run a heuristic-based solver:
- For each pending order: compute candidate couriers within radius.
- Score each candidate: distance to restaurant + ETA delta + batchability with their existing orders.
- Greedy assignment in priority order; refine periodically.

### Matching cadence
- Don't match instantly — wait ~10–20 sec to batch.
- Re-match orders that haven't been picked up if a better courier appears.
- Once courier accepts, lock the assignment.

## 8. ETA: the four-component beast

A delivery ETA is the sum of:
- **Order preparation time** (cooking) — varies by restaurant + item + current load.
- **Courier-to-restaurant drive time** — based on traffic.
- **Restaurant-to-customer drive time** — based on traffic.
- **Wait time at restaurant** — courier arrived but food isn't ready.

ETA is a **machine-learned regression** model trained on millions of past deliveries:
- Features: restaurant, time-of-day, item complexity, courier vehicle, weather, current traffic.
- Output: P50 + P90 ETA.

Update every 30 sec as conditions change. Show customer a range ("25–35 min"), not a false-precision single number.

## 9. Batching: the cost lever

DoorDash makes ~$5 per single delivery; ~$8 per batched (two orders) one with the same courier. Margin difference is enormous.

**Batching constraints:**
- Same restaurant or nearby (no zigzag).
- Both orders' SLA still met.
- Courier has bag capacity.
- Some items don't batch (pizza ≠ ice cream).

The matching solver above naturally finds batches when scoring multi-stop routes. Batching ratio (% of deliveries batched) is a key business KPI — typically 30–50%.

## 10. Surge pricing & courier incentives

Three-sided pricing:
- **Customer-facing surge** — busy time / weather → +20–50% delivery fee.
- **Courier incentives** — base pay + tips + bonuses for "complete N orders by 8pm" or "go to underserved area."
- **Restaurant boost programs** — restaurants pay for promoted placement.

Surge calculation = stream-processed (Flink/Kafka Streams) over current order volume vs courier supply per geo cell, updated every minute. Same shape as [Uber surge](/blog/system-design/design-uber-ride-sharing).

## 11. Real-time tracking

Customer wants to see "Courier is 5 min away."

- Courier app posts location every 4–10 sec.
- Each ping → in-memory store (Redis) keyed by `courier_id`.
- For customer's order's view, the customer app subscribes via WebSocket; backend pushes courier's location updates.
- Don't expose courier's exact identity (privacy) — just the moving dot.
- Recent path also stored for "Why was the courier delayed?" debugging.

This is the same engine as [Uber](/blog/system-design/design-uber-ride-sharing).

## 12. Settlement: the financial backbone

Every order generates 5+ ledger entries:
- Customer charged: $25.
- Restaurant earns: $18 (after platform fee + commission).
- Courier earns: $5 base + tip.
- Platform takes: $2 commission + $1 delivery fee.
- Sales tax to government: $1.

End-of-day batch:
- Restaurant payouts (T+1 to bank).
- Courier payouts (typically weekly).
- Platform revenue rolled to treasury.

The architecture is exactly **[Design a Payment System](/blog/system-design/design-payment-system)** — double-entry ledger, reconciliation pipeline, immutable financial records.

## 13. Failure modes

| Failure | Handling |
|---|---|
| **Restaurant doesn't accept order** | Auto-cancel after 5 min; refund customer; mark restaurant offline if it happens repeatedly |
| **No courier available** | After N retry rounds, cancel and refund; track for capacity planning |
| **Courier accepts then ghosts** | Re-match to new courier; small penalty to original |
| **Wrong items delivered** | Customer disputes via support; refund out of restaurant's payout |
| **Restaurant tablet offline** | Fall back to phone call automation; still accept orders, route to rescue queue |
| **Hot meal goes cold (SLA breach)** | Customer credit issued automatically; courier gets reduced rating |

## 14. The trade-offs interviewers will probe

| Question | What they want to hear |
|---|---|
| "Three-sided marketplace — what's hard?" | Each side has different incentives + latency constraints |
| "Why batch deliveries?" | Margin lever; needs route-optimization solver |
| "ETA components?" | Cooking + drive-out + drive-in + wait — all stochastic |
| "How does the courier matching work?" | Optimization with batching, not greedy nearest |
| "Catalog updates in real time?" | Restaurant tablet → Kafka event → cache invalidation + customer push |
| "What if no courier accepts?" | Re-match rounds; eventual cancel + refund |
| "How does this differ from Uber?" | Cooking time + catalog + restaurant side |

## 15. The 30-second summary

> Food delivery is a three-sided marketplace where each side has unique state. The **catalog** (millions of restaurants × items, real-time updates), the **order pipeline** (idempotent state machine across customer + restaurant + courier), the **matching** (route-optimizing solver, not nearest-driver), and the **ETA** (cooking + driving) all interact. Batching is a margin lever; surge balances supply and demand. Settlement is double-entry ledger with daily payouts to restaurants and couriers.

Lead with the three-sided model. Show the order state machine. Differentiate matching/ETA from rides — cooking time is the unique input. Mention batching as the business lever. That's the staff-level answer.
