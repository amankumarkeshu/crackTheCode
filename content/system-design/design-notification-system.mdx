Every product needs notifications. Almost no product builds them well. The interview version of this question seems trivial ("we'll just call SES") but the production-grade design has to answer: how do you avoid spam? Provider failover? Per-user rate limits? Template versioning? Compliance (TCPA, GDPR)? Idempotent delivery without dupes?

This is the post for the senior-level notification design.

## 1. Clarify before you draw

- **Channels?** Push (APNs, FCM), email (SES, SendGrid), SMS (Twilio), in-app, webhooks?
- **Volume?** 1M/day or 1B/day? (Determines architecture decisions.)
- **Latency?** Real-time (chat alerts), batch (daily digest), or both?
- **Templating?** Localization (i18n)?
- **User preferences?** Per-channel opt-in/out granularity?
- **Compliance?** Quiet hours? GDPR right-to-erasure?

For this post: 4 channels (push/email/SMS/in-app), 100M users, ~500M notifications/day, real-time + scheduled, full template + i18n + preference management.

## 2. Functional & non-functional requirements

**Functional:**
1. App service triggers notification: `notify(user_id, template, data, channels)`.
2. System renders, applies preferences, dispatches via right provider.
3. Tracks delivery status (sent, delivered, opened, clicked, bounced).
4. Honors per-user opt-in/out, quiet hours, rate limits.
5. Supports scheduled and recurring notifications.

**Non-functional:**
1. **At-least-once delivery** with idempotent dedup so users don't see duplicates.
2. **Low latency** for real-time alerts (&lt;5 s end-to-end).
3. **Provider failover** — if SES is down, email shouldn't stop globally.
4. **Highly available** — notification outage hides all your other features' value.
5. **Auditable** — for compliance + debugging.

## 3. Capacity numbers

- 500M notifications/day → ~6K/s average, ~50K peak.
- Multi-channel fan-out: 1 trigger × ~2 channels avg = ~12K dispatches/sec.
- Each dispatch ≈ 1 KB → ~12 MB/s through the pipeline.
- Storage of delivery logs: 500M × 365 × 2 yrs × 200 B = ~75 TB.

Fan-out and provider concurrency limits drive the architecture.

## 4. The pipeline

```
App Service ─► Notification API
                    │
                    ▼
              Rules Engine        (apply preferences, rate limits, quiet hours)
                    │
                    ▼
              Template Renderer    (i18n, personalization)
                    │
                    ▼
              Channel Routers (one queue per channel: push / email / sms / in-app)
                    │
            ┌───────┼───────┬─────────┐
            ▼       ▼       ▼         ▼
         APNs    SES    Twilio   In-app store
                    │       │         │
                    └───────┴────►  Delivery Tracking
```

Each box is a separate service. Each channel queue lets you scale independently and apply per-channel concurrency limits / provider quotas.

## 5. Rules engine — the part that prevents lawsuits

Before any notification sends, run a **chain of filters**:

1. **User preference check** — has the user opted out of this notification type or this channel?
2. **Rate limit** — has this user received &gt; N notifications in the last hour? (Per-channel + global.)
3. **Quiet hours** — is it 2 AM in the user's timezone? Suppress non-critical or queue for morning.
4. **Compliance gate** — TCPA / GDPR / CAN-SPAM check; e.g. SMS must have explicit consent.
5. **Dedup window** — has the same `(user, dedup_key)` been notified in the last X hours?

Each filter can suppress, delay, or downgrade (e.g. push → in-app fallback). **A notification system without a rules engine is a spam system.**

## 6. Template management

Notifications are templates + data, not hand-built strings:

```yaml
- id: order_shipped_v3
  channels: [push, email]
  versions:
    en:
      push:  "Your order #{{order_id}} is on the way! ETA: {{eta}}."
      email:
        subject: "{{order_id}} shipped"
        body_html: "..."
    es:
      push:  "Tu pedido #{{order_id}} está en camino..."
```

Stored in a config service or content DB. Versioned (changes are tracked, never overwritten — for compliance and A/B testing). Localized per user's locale. Pre-compiled into renderable form for hot-path performance.

## 7. Provider abstraction

Each channel has 2+ providers behind a unified interface:

```python
class PushProvider(ABC):
    def send(self, device_token, payload) -> DispatchResult: ...

class APNsProvider(PushProvider): ...   # Apple
class FCMProvider(PushProvider): ...    # Google
```

The router picks based on:
- Device platform (iOS → APNs, Android → FCM).
- **Provider health** (circuit-breaker per provider; if SES bounce rate spikes, route email through SendGrid).
- Cost (some providers are cheaper for low-priority traffic).

## 8. Delivery guarantees

The promise: **at-least-once delivery with deduplication so users see at-most-one**.

Mechanism:
- Each notification gets a `notification_id` (Snowflake) at API-receive time.
- Each `(user_id, dedup_key)` is checked against a Redis dedup window before send.
- The provider call is idempotent on `notification_id` (most providers support a request-id header for retry safety).
- If the provider responds 5xx, retry with exponential backoff up to N times.
- If still failing after retries, dead-letter queue + alert.

Result: a notification might be *attempted* multiple times by your system, but the user sees one delivered message.

## 9. Async + scheduled

All non-immediate notifications go through a queue (Kafka or SQS):

```
notify() → notification_id assigned → enqueued
   ↓
Worker pool consumes → applies rules → renders → dispatches
```

For **scheduled** notifications (digest at 8 AM, reminder in 1 hour):
- Persist to a `scheduled_notifications` table with `dispatch_at` timestamp.
- A small fleet of cron-style workers polls "WHERE dispatch_at &lt; now() ORDER BY dispatch_at LIMIT 1000" every few seconds.
- Move to the live queue when due.

For very high volumes of scheduled jobs, see [Design a Distributed Job Scheduler](/blog/system-design/design-distributed-job-scheduler).

## 10. Per-channel deep dives

### Push (APNs / FCM)
- Stateless from your side; provider holds the device-to-user binding.
- Token rotation is a real headache: tokens expire, are invalidated on app uninstall, etc. Update on every login + handle "InvalidToken" responses.

### Email
- Bounce handling is mandatory. Hard bounce → mark address invalid, never retry.
- Reputation matters — too many bounces and your sending domain gets blocklisted by Gmail.
- Track unsubscribe links per template/version for compliance.

### SMS
- Most expensive channel by 100×. Reserve for critical (OTP, fraud alerts).
- Country-specific compliance (TCPA in US, TRAI in India). Send-time windows are regulated.
- Long-code vs short-code vs alphanumeric sender ID — each has different constraints.

### In-app
- Persisted in a per-user inbox table. Read on login.
- Real-time delivery via WebSocket if the user is connected (see [WhatsApp post](/blog/system-design/design-whatsapp-chat)).

## 11. Observability

A notification system is a **black box without metrics**. Track:

- Per-channel: throughput, error rate, latency, provider status.
- Per-template: open rate, click rate, conversion.
- Per-user: rate-limit hits, complaint rate.
- End-to-end: notify() → user sees it (latency distribution).

Sample every dispatch with full trace (template version, user prefs evaluated, provider chosen) into a queryable log store. When a user complains "I got 5 emails," you need to find every step in seconds.

## 12. The trade-offs interviewers will probe

| Question | What they want to hear |
|---|---|
| "How do you avoid sending duplicates?" | Idempotency on `notification_id` + dedup window on `(user, dedup_key)` |
| "What if a provider goes down?" | Circuit-breaker + fallback provider; per-channel queue isolates blast radius |
| "How do you handle 50K dispatches/sec?" | Per-channel parallel queues; horizontal worker pools |
| "How do you respect user preferences?" | Rules engine *before* render; preferences in a fast cache |
| "How do you support i18n?" | Templates have per-locale variants; choose at render time based on user.locale |
| "Compliance?" | Audit log every dispatch with the rules eval; honor unsubscribes within seconds |
| "How would you build daily digest emails?" | Scheduled job aggregates events per user; one email instead of 100 push notifications |

## 13. The 30-second summary

> A notification system is a **fan-out pipeline with a rules engine in front and per-channel provider abstraction at the back**. Idempotency keys + dedup windows give at-least-once delivery without duplicates. Each channel has its own queue and its own concurrency budget. Compliance and observability are first-class, not afterthoughts. Real failure modes are spam complaints and provider blocklisting, not throughput.

Land that with a clean separation of "decide whether to send" (rules engine) from "actually send" (provider routing), and you've answered the senior-level question well.
