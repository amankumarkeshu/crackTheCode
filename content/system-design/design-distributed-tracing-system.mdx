In a microservices world, a single user request fans out to dozens of services. When something is slow or wrong, you need to **trace** that request across all hops to see where the time went. Building a system that does this at scale (millions of spans/sec, queries returning in seconds) is its own design problem. Jaeger, Tempo, AWS X-Ray, Datadog APM, Honeycomb, Lightstep, they all solved this in slightly different ways.

## 1. Clarify before you draw

- **In-house only**, or supporting customer SDKs (a SaaS product like Datadog)?
- **Span volume?** ~100K (small startup) to ~50M spans/sec (large e-comm).
- **Retention?** 7 days hot, 30 days warm, 90+ days cold?
- **Tail-based sampling needed?** (i.e. decide *after* seeing the full trace whether to keep it.)
- **What types of queries?** Trace-by-id, find-slow-traces, service-dependency graph?

For this post: in-house OpenTelemetry-compatible tracer ingesting ~10M spans/sec across thousands of services; queries by trace ID, slow-trace search, and service-graph computation.

## 2. The span model

Industry-standard: **OpenTelemetry**.

```
Trace 7a3f...                                      
├── Span: HTTP /checkout (gateway)                 [duration: 1240 ms]
│   ├── Span: getCart (cart-svc)                   [duration: 45 ms]
│   ├── Span: getInventory (inventory-svc)         [duration: 80 ms]
│   ├── Span: chargeCard (payment-svc)             [duration: 1080 ms]  ← culprit
│   │   └── Span: stripeAPI                        [duration: 1050 ms]
│   └── Span: sendEmail (notif-svc)                [duration: 30 ms]
```

Each span has:
- `trace_id` (128-bit), same for all spans in this request.
- `span_id` (64-bit), unique per span.
- `parent_span_id`, defines the tree structure.
- `service`, `operation`, what was being done.
- `start_ts`, `duration`, timing.
- `attributes` (tags), arbitrary key-values: `http.status=200`, `db.query=SELECT...`.
- `events` (logs), timestamped messages within the span.

Trace-id is propagated via HTTP headers (`traceparent`) or message headers (Kafka). When service A calls B, A's outgoing request carries the trace-id; B reads it and emits its own spans under that trace.

## 3. Functional & non-functional requirements

**Functional:**
1. SDK in every service emits spans.
2. Spans collected, stored, indexed.
3. UI: enter trace ID → see waterfall.
4. Search: "all traces with `error=true` from `payment-svc` in last hour."
5. Service map: derived from spans showing service-to-service call graph.
6. Alerting: error-rate spike, latency P99 spike on a service.

**Non-functional:**
1. **Low overhead in instrumented services**, adding tracing must not slow the app.
2. **High ingestion rate**, millions of spans/sec.
3. **Query latency**, &lt;5 sec for trace-id lookup; &lt;30 sec for search.
4. **Cost-efficient storage**, spans are voluminous and mostly useless after 7 days.

## 4. Capacity numbers

- 10M spans/sec, ~500 bytes each = **5 GB/sec ingest = 432 TB/day**.
- With 7-day retention: ~3 PB hot.
- ~1B traces/day (10M spans / ~10 spans-per-trace).
- Query rate: ~100/sec (trace lookups by humans + a few automated).

The ingest rate is the dominant scaling constraint.

## 5. The pipeline

```
   Apps (instrumented w/ OpenTelemetry SDK)
         │
         ▼

         │ batches, retries, may sample
         ▼
   Ingestion Gateway (load-balanced)
         │
         ▼

         │
         ▼

   ▼     ▼      ▼             ▼

```

## 6. Sampling: the cost vs fidelity decision

You can't store every span. At 10M spans/sec for 7 days, that's literally petabytes of data, most of which is repetitive normal-case traces.

### Head-based sampling
At trace start, flip a coin (e.g. 1% probability) → if "heads," emit all spans for this trace; otherwise drop them all.
- **Pro:** simple, cheap (no storage even for dropped traces).
- **Pro:** consistent, either you have the whole trace or none.
- **Con:** decision happens before knowing if the trace is interesting (errors, slow). 99% of errors get dropped.

### Tail-based sampling
Spans buffered for ~30 sec; once trace finishes (or times out), decision is made: keep if interesting (error, slow, sampled), drop otherwise.
- **Pro:** can keep all error/slow traces.
- **Con:** must buffer 30 sec of spans → memory-heavy.
- **Con:** spans of a trace might span multiple machines, buffer must be partitioned by trace_id.

### Adaptive / probabilistic sampling
Sample more aggressively for healthy services; sample everything for services with elevated error rate.

Real-world setups combine all three. Head-based at the SDK (1% baseline), tail-based at the collector (keep all errors + slow), adaptive on top.

## 7. Storage: the hardest part

Each span is small (~500 bytes) but with billions per day, you need:

### Trace-id index
Lookup by trace_id must be sub-second. Index spans by `trace_id` → list of spans.
- Cassandra / DynamoDB / Bigtable, keyed by trace_id, partitioned for write throughput.
- Tempo (Grafana) and Jaeger use object storage (S3) with a smart blob format (e.g. all spans of a trace stored together by trace-id prefix).

### Search index
"Find all traces where `service=payment-svc AND error=true AND duration > 1s` in the last hour."
- Build inverted index (Elasticsearch / OpenSearch) on each span's tags + service + duration buckets.
- Index size: ~10–20% of raw span data.
- Costly, many tracing systems index only a subset of attributes.

### Service graph
Derived metric: the call-graph between services (which calls which, with what error rate / latency).
- Stream-process spans with Flink/Kafka Streams.
- Roll up minute-by-minute: `(caller, callee, count, error_count, p99_latency)`.
- Store in time-series DB (Druid / ClickHouse) for fast UI queries.

## 8. Storage tiers

```
Hot (last 24 hr)   → Cassandra/DynamoDB
                     - Random access by trace_id
                     - Full search index on Elasticsearch

Warm (1–7 days)    → S3 in Parquet
                     - Cheaper; slightly slower lookup
                     - Reduced search index

Cold (7+ days)     → Glacier / object archive
                     - Compliance only; not queryable cheaply
                     - Or just delete, depends on retention policy
```

Tempo and similar modern tracers go S3-only + an object-storage-friendly index format. Jaeger originally used Cassandra; later versions added S3 backend.

## 9. The query path

### Trace-by-id
1. Lookup trace_id in primary index → list of object-storage offsets.
2. Fetch span blobs from S3 in parallel.
3. Reconstruct waterfall by parent_span_id → render UI.

Latency target: ~1 sec.

### Search
1. Query parser → translates user filter to Elasticsearch DSL.
2. ES returns matching trace_ids.
3. For each trace_id, fetch full trace (or just metadata for the list view).

Latency target: ~5–30 sec depending on time range.

### Service graph
Pre-aggregated; just query Druid/ClickHouse.

## 10. Reducing data volume: span aggregation

Most spans aren't queried individually. Pattern: aggregate similar spans into RED metrics.

- **R**ate, **E**rrors, **D**uration, per (service, operation) per minute.
- Stream from raw spans into a metrics service.
- These metrics are queryable forever cheaply.
- Raw spans dropped after retention.

Honeycomb and similar use a different trick: **span-level columnar storage** (each attribute is its own column), letting per-attribute aggregations be very fast even over weeks of data.

## 11. Service mesh integration

Modern systems use **service meshes** (Istio, Linkerd) that auto-emit spans for every HTTP/gRPC call without app-level instrumentation. The mesh sidecar (Envoy) emits spans, propagates trace headers, integrates with the OTel collector.

Pros: zero app code changes for basic tracing. Cons: doesn't capture in-process operations (you still need SDK for that).

## 12. Cardinality: the hidden killer

Every unique combination of `(service, operation, status, ...)` is a metric "series." If your URL is `/users/{id}/orders` and you tag the span with `path=/users/12345/orders`, you've created a series per user, billions of series. Storage explodes.

Discipline:
- **Don't** put high-cardinality values (user IDs, request IDs, session tokens) as **tags**.
- **Do** put them as **logs/events** within the span (still queryable, not indexed for aggregation).
- The SDK + collector should normalize (`/users/{id}/orders` instead of the actual ID).

This is one of the top things distinguishing senior from junior in observability.

## 13. Failure handling

| Failure | Behavior |
|---|---|
| **Collector down** | SDK buffers in memory + retry; on overflow, drops |
| **Ingestion gateway saturated** | Backpressure to collector; SDK keeps backing off |
| **Search index down** | Trace-by-id still works (different store); search degraded |
| **Storage full** | Reject new spans; alert; raise sampling rate to recover |

Tracing is "best-effort", never block production traffic for tracing.

## 14. The trade-offs interviewers will probe

| Question | What they want to hear |
|---|---|
| "Head- vs tail-based sampling?" | Head is cheaper but misses errors; tail catches errors but needs buffering |
| "How do you achieve sub-second trace lookup over PB?" | Keyed by trace_id; co-locate spans for one trace; SSD index over S3 blobs |
| "Cardinality? How do you control it?" | Normalize paths; don't tag with unbounded values |
| "How is search implemented?" | Elasticsearch over span attributes |
| "Why service mesh integration?" | Zero-code instrumentation for inter-service calls |
| "What's the storage cost shape?" | Hot DB → S3 Parquet → archive; index-only on hot tier |
| "Trace propagation across async (Kafka) boundaries?" | trace_id in message headers; consumer creates child spans |

## 15. The 30-second summary

> A distributed tracing system is **OpenTelemetry SDKs emitting spans → collector pipeline with head- and tail-based sampling → trace-id-keyed storage (often S3 with smart layout) plus search index (Elasticsearch) plus stream-processed service graph (Flink → Druid)**. Key trade-offs: cost vs fidelity (sampling), cardinality discipline (don't index user IDs), and storage tiering (hot DB + warm S3 + cold delete). Tracing must be **best-effort**, never block production traffic.

Lead with the span model + propagation. Show head vs tail sampling explicitly. Explain trace-id-keyed lookup vs search-index lookup as two distinct paths. Mention cardinality. That's the staff-level answer.
