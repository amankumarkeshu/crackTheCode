Ad serving sits at the most demanding intersection of **latency, scale, and money** in software. Every page load runs a real-time auction; the ad must render in under 100 ms; the platform handles billions of impressions a day; revenue depends on getting every step right. If you're interviewing at Google Ads, Meta Ads, Amazon Ads, The Trade Desk, AppLovin, or any ad-tech company, this is your question.

## 1. Clarify before you draw

- **Are we the ad exchange, the SSP, the DSP, or all-in-one?** (Briefly: SSP = supply side, sells publisher inventory; DSP = demand side, advertisers bid; Exchange = matchmaker.)
- **Display ads, video ads, or both?**
- **Targeting?** Demographic, contextual, behavioral?
- **Latency budget?** RTB (real-time bidding) is a hard 100 ms; in-house serving might be 50 ms.
- **Scale?** ~10B requests/day (mid-size platform) to ~1T (Google).

For this post: an end-to-end system where publishers send ad requests, an auction selects an ad, advertisers' campaigns are matched to inventory, with ~100B requests/day.

## 2. Functional & non-functional requirements

**Functional:**
1. Receive ad request (publisher: app/website + user context).
2. Match request to eligible ads from active campaigns.
3. Run auction, pick winner.
4. Return winning ad creative.
5. Track impression, click, conversion.
6. Apply frequency caps, budget limits, brand-safety rules.
7. Bill advertisers; pay publishers.

**Non-functional:**
1. **Latency:** &lt;100 ms ad-request to response.
2. **Scale:** millions of req/sec at peak.
3. **Correctness:** budgets must not over-spend; frequency caps must hold.
4. **Fraud detection:** bot traffic, click farms.
5. **Privacy compliance:** GDPR, CCPA, ATT.

## 3. Capacity numbers

- 100B ad requests/day = ~1.2M/sec avg, ~3M/sec peak.
- Per request: 100 ms hard budget. Most of it is network; the system has maybe ~40 ms internally.
- ~10K concurrent advertisers, ~100K active campaigns.
- ~5B impressions/day * couple of clicks per 1000 = ~10M clicks/day.
- ~2B daily users with ~200 features each in the user profile store.

## 4. The auction request flow

```
Publisher (e.g. NYT app)  ←── user opens app ────
        │                                       
        │ 1. Ad request (SDK/API)
        ▼
   SSP / Exchange ───── 2. broadcast bid request to N DSPs ───┐
        │                                                       │
        │           ┌──────────────────────────────────────────┘
        │           ▼
        │     DSP A   DSP B   DSP C   ...    (each runs internal auction)
        │       │       │       │
        │       └─────┬─┴───────┘
        │             ▼
        │      bids return
        │
        ▼
   Auction Engine (second-price)
        │
        ▼
   Winning DSP's creative ID returned
        │
        ▼
   Creative delivered to publisher
        │
        ▼
   Impression event recorded
```

For an in-house ad system (Facebook, Google), there's no external bid auction — internal pacing/auction picks the best ad from the platform's own advertisers. We'll cover both.

## 5. Inside a DSP: the matching pipeline

A DSP receives a bid request `{user_id, geo, page_context, ad_size, ...}` and must respond within ~30 ms with a bid + creative.

```
Bid Request
    │
    ▼
Inventory Filter
    │ - Brand safety (publisher allowed?)
    │ - Geo / device / format match
    │ - Frequency cap enforcement (Redis check)
    ▼
Candidate Generation
    │ - From campaigns targeting this user/context
    │ - 1000s of candidates → narrow to ~100
    ▼
Pacing & Budget Check
    │ - Has campaign budget remaining today?
    │ - Pacing plan: spend $500 by 2pm, $1000 by 5pm
    ▼
ML Scoring (predicted CTR / CVR)
    │ - For each candidate: predict click probability
    │ - Bid = predicted_value × adjustment
    ▼
Top Bid Selected
    │
    ▼
Bid Response: {bid_amount, creative_id, ad_markup}
```

Every stage must finish in microseconds. **Total internal budget &lt;30 ms.**

## 6. Candidate generation: how do you filter 100K campaigns in 5 ms?

Build an **inverted index** of campaigns by their targeting:
- `geo:US-CA → [campaign_42, campaign_99, ...]`
- `interest:gaming → [campaign_99, campaign_512, ...]`
- `device:mobile → [campaign_42, campaign_99, ...]`

For a request, intersect posting lists for each matching attribute → narrow to candidates. (Same shape as [Google Search](/blog/system-design/design-google-search) inverted index.)

For very high-cardinality features (specific user segments, retargeting lists), use Bloom filters or per-user precomputed candidate lists ("for this user, eligible campaigns are X, Y, Z" updated daily).

## 7. ML scoring: pCTR / pCVR prediction

For each candidate, predict probability of click (pCTR) and conversion (pCVR). Then:

`bid = pCTR × pCVR × value_per_conversion`

This must be evaluated in microseconds per candidate. Real systems use:
- **Logistic regression** with hashed feature crosses (Vowpal Wabbit, Field-aware FM).
- **Two-tower deep learning** (user-tower precomputed daily; item-tower precomputed; final dot product is fast).
- Quantized models running in C++ with custom inference engines.

Not a 1-billion-parameter LLM. The latency budget rules that out.

## 8. Frequency capping & budget pacing

### Frequency cap
"Don't show this user this ad more than 3× per day."

- Counter in Redis keyed `(user_id, campaign_id, day)`.
- Increment on serve; reject if &gt;= cap.
- Eventually-consistent — the user might see 4 in the same minute due to Redis lag, but it converges.
- Use a [Distributed Counter](/blog/system-design/design-distributed-counter) sharded by user.

### Budget pacing
A $100K daily budget shouldn't all spend in the first hour.
- Pacing engine computes "spend curve" per campaign per hour.
- Real-time check: if today's spend ahead of curve, reduce eligibility (e.g. only bid 10% of requests).
- Token-bucket-style throttle, replenishing per minute.
- This is a [Rate Limiter](/blog/system-design/design-rate-limiter)-shaped problem.

Both must be sub-millisecond on the request path.

## 9. The tracking pipeline (impressions, clicks, conversions)

When the user sees an ad → publisher fires an **impression pixel**: `GET https://track.adserver.com/imp?id=...`.

When user clicks → click event fires.

When user buys after clicking → conversion event fires (often days later, via different SDK).

This is **ingestion at billions/day**:
- Edge collectors at CDN scale (cross-link to [Design a CDN](/blog/system-design/design-cdn)) absorb the load.
- Append-only to Kafka.
- Real-time aggregation (Flink) updates per-campaign counters.
- Long-term storage in a columnar warehouse (BigQuery, Snowflake).

## 10. Attribution: who deserves credit?

Multiple ads might "touch" a user before they convert:
- Saw display ad on Mon.
- Saw video ad on Wed.
- Clicked search ad and bought on Fri.

Different **attribution models** assign credit:
- **Last-click** — only the search ad gets credit.
- **First-touch** — only the display ad.
- **Linear** — each gets 1/3.
- **Time-decay** — recent touches get more.
- **Data-driven** — ML model attributes credit based on observed lift.

The attribution pipeline is a **batch + stream hybrid**:
- Stream: assign provisional last-click attribution in real time.
- Batch: nightly recompute with full multi-touch model.

Privacy regulations (Apple's ATT, Google's Privacy Sandbox) are reshaping attribution dramatically — increasingly, attribution happens via aggregated, k-anonymized reports rather than per-user tracking.

## 11. Fraud detection

Estimated 20–30% of online ad traffic is fraudulent. Fraud takes many forms:
- **Bot traffic** — non-human clicks/impressions.
- **Click farms** — humans paid to click.
- **Domain spoofing** — fraudulent publisher claims to be NYTimes.
- **Pixel stuffing** — invisible 1×1 ad iframes claiming impressions.

Detection is multi-layered:
- **Real-time** — heuristics on the request: known bot UAs, abnormal click rate, geo mismatch.
- **Batch ML** — cluster analysis on user behavior; outliers flagged.
- **IVT (Invalid Traffic) lists** from third parties (HUMAN/White Ops, Integral Ad Science).

Fraud invalidates billed impressions; budgets are credited back. Critical for advertiser trust.

## 12. Creative delivery

The winning ad's actual content (image, video, HTML5) must render. Two patterns:
- **CDN-served** — creative URL → fetched from CDN ([Design a CDN](/blog/system-design/design-cdn)).
- **Inline-returned** — for tiny creatives, full HTML markup returned in bid response.

Pre-cache hot creatives at edge globally. Latency-critical for video; cold-start delay = lost impression.

## 13. Storage: the data layout

| Data | Store | Why |
|---|---|---|
| User profiles (segments, history) | Distributed KV (Cassandra/Bigtable) | Per-user reads; high write rate |
| Campaign metadata | RDBMS (Postgres) | Transactional; modest size |
| Inverted index for matching | In-memory + RocksDB | Sub-ms lookups |
| Frequency caps | Redis | Sub-ms increment |
| Impression / click events | Kafka → BigQuery / S3 | Append-only firehose |
| Real-time aggregates | Druid / ClickHouse | Sub-second campaign dashboards |
| Long-term reports | Data warehouse | Daily / weekly reports |

## 14. Privacy & compliance

Modern ad systems must:
- **Honor opt-out** — IDFA on iOS, GAID on Android. If user opted out, no targeting/tracking.
- **Cookie-less paths** — first-party data, contextual targeting only.
- **GDPR consent** — show banner; only operate per-user-consent.
- **Data residency** — EU users' data stays in EU (cross-link to [Design a Distributed Cache](/blog/system-design/design-distributed-cache)'s region discussion).

Every system component must be designed around the consent flag. Privacy is now a first-class architectural concern, not a feature.

## 15. The trade-offs interviewers will probe

| Question | What they want to hear |
|---|---|
| "How do you fit candidate generation in 5 ms?" | Inverted index over campaign targeting attributes |
| "How do frequency caps stay correct under load?" | Redis-backed counters; eventual consistency acceptable |
| "How do you pace budgets?" | Token bucket per campaign; pacing curve over the day |
| "First-price vs second-price auction?" | Second-price truthful but rare in practice; first-price now dominant in RTB |
| "How does attribution work with multiple touchpoints?" | Stream provisional + batch recompute; multi-touch models |
| "How is impression tracking exactly-once?" | It's not — eventual consistency with idempotency keys; reconciliation against publisher logs |
| "Privacy / cookie deprecation impact?" | Cohort-based targeting; first-party data; aggregated attribution reports |

## 16. The 30-second summary

> An ad serving system runs **a sub-30-ms internal auction over an inverted-indexed campaign catalog with ML-based pCTR/pCVR scoring, frequency-cap and budget-pacing constraints, and per-impression tracking ingested at billions/day**. The hardest constraints are the latency budget, billing correctness (no over-spend), and fraud + privacy. Attribution is a hybrid stream + batch problem; long-term, the entire industry is moving toward aggregated, privacy-preserving reporting.

Lead with the latency budget — it shapes everything. Show the auction pipeline and how candidate generation works. Mention frequency caps + budget pacing. Talk fraud + privacy as architecture-level concerns. That's the staff-level answer.
