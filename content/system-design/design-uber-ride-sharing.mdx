If you're interviewing at Uber, Lyft, DoorDash, Swiggy, Zomato, Grab, Bolt, or any other "match a buyer with a moving seller" company, **you will get this question**. It's actually three problems stitched together: a **high-write geospatial index**, a **matching engine**, and a **trip lifecycle state machine** with strict consistency requirements.

## 1. Clarify before you draw

- **Service type?** Ride-share (Uber), food delivery (DoorDash), parcel (Lyft delivery)? They share 80%, differ in matching constraints.
- **Real-time matching latency?** &lt;5 sec from request to driver assignment.
- **Driver location update frequency?** Every 4 seconds is the Uber default.
- **Surge pricing?** ETA prediction?
- **Fleet sizes?** ~5M drivers, ~100M monthly riders.
- **Geographic granularity?** City-level, country-level, global?

For this post: ride-sharing, ~5M drivers, ~100M MAU, 25M trips/day, ~5K matches/sec at peak.

## 2. Functional & non-functional requirements

**Functional:**
1. Driver app reports location every 4s.
2. Rider requests a ride (origin, destination).
3. Match rider with nearest available driver.
4. Track trip in real time (status, location).
5. Compute fare; settle payment.
6. Surge pricing in high-demand zones.

**Non-functional:**
1. **Match latency** &lt;5 s end-to-end.
2. **High write throughput** for location updates.
3. **Strong consistency** for matching (no double-booking a driver).
4. **Eventual consistency** for "where is my driver" (some staleness OK).

## 3. Capacity numbers

- **5M drivers × 1 update / 4 s** = **~1.25M writes/sec** for location updates. Pure write load.
- **25M trips/day** = ~300 trips/sec average, ~5K peak.
- **Each location update**: (driver_id, lat, lng, heading, timestamp) ≈ 30 bytes → ~40 MB/s ingress for location alone.
- Trips storage: 25M × 365 × 5 yrs × ~2 KB = **~90 TB** raw.

The write rate on location updates dominates the architecture.

## 4. Geospatial indexing — pick exactly one scheme

You need to answer "find all available drivers within 2 km of (lat, lng)" in milliseconds. Three viable schemes:

### A. Geohash (string-based, simple)

Encode (lat, lng) into a base32 string where common prefixes = nearby points:

```
San Francisco roughly: "9q8yyk"
6 chars ≈ 1.2 km × 0.6 km cell
```

Lookup: take rider's geohash prefix, query all drivers whose geohash shares that prefix.

- **Pros:** trivially indexable in any KV store; sortable.
- **Cons:** *boundary problem* — two points right next to each other can have totally different prefixes if they straddle a cell edge. Mitigate by querying the cell + 8 neighbors.

### B. S2 cells (Google's hierarchical scheme)

Earth is divided into 6 cube faces, each subdivided into a hierarchy of cells. A point gets a 64-bit S2 cell ID. Cells at level 14 are ~250 m × 250 m.

- **Pros:** much better boundary behavior; built-in hierarchical zooming; native multi-resolution.
- **Cons:** more complex; requires the S2 library.
- **Verdict:** what Google Maps and many production geospatial systems use.

### C. Quadtree (in-memory, dynamic)

Recursively subdivide a 2D region into 4 quadrants until each leaf has ≤ N points. Search descends the tree.

- **Pros:** adapts to point density (urban areas get fine cells; rural stays coarse).
- **Cons:** stateful; tricky to shard; rebuild cost on heavy writes.
- **Verdict:** used in-memory inside matching workers, not as the primary store.

**Real Uber:** geohash-based primary store + per-region in-memory quadtree on matching workers.

## 5. Architecture overview

```
Driver App ─WebSocket─► Location Service ─► Hot Store (Redis Geo / sharded by geohash prefix)
                                            │
                                            └─► Cold Store (Cassandra, 30-day retention)

Rider App  ─REST─► Trip Service ─► Matching Engine ─► (queries Location Service)
                       │
                       ▼
                  Trip DB (Postgres / DynamoDB, sharded by trip_id)

Pricing Service (surge zones, ETA)  ──► reads from Location aggregates
```

## 6. The location update path

1.25M writes/sec is the peak. Naive: write each to the DB → death.

Hot path:
1. Driver's app pushes update over a long-lived connection (gRPC stream or WebSocket) to the **Location Service**.
2. Location Service writes to **Redis** (`GEOADD` if you use Redis Geo; otherwise a sorted-set keyed by geohash prefix).
3. Redis is sharded by geohash prefix (4-char prefix → ~10K shards).
4. Asynchronously, an aggregator batches updates and writes to Cassandra for the 30-day "where was the driver" trail.

Trade-off: Redis Geo's `GEOADD` is convenient but uses a single sorted set per key — hot prefixes (downtown SF) become hot shards. Mitigate by:
- Sharding by 5-char geohash prefix (smaller cells, more shards).
- Replicating hot prefixes across multiple Redis nodes.
- See [hot-key protection](/blog/system-design/design-distributed-cache#9-hot-key-protection).

## 7. The matching engine

Rider request arrives → Trip Service creates a trip row (status: `REQUESTING`) → calls Matching Engine.

```
1. Get rider's geohash prefix.
2. Query Location Service for all available drivers within 2 km
   (start with 6-char prefix; widen to 5-char if no candidates).
3. Filter: only drivers in AVAILABLE state, vehicle type matches request,
   ETA budget matches, not blacklisted by rider.
4. Score each candidate (proximity, driver acceptance rate, recent earnings, etc.).
5. Send dispatch offer to top driver via push to their app.
6. Wait up to ~10s for accept/decline.
7. If declined or timed out, offer to next driver.
8. On accept: atomic CAS on trip status REQUESTING → MATCHED.
   Driver state DB is updated to ON_TRIP.
9. Return trip details to rider.
```

The CAS on step 8 is critical — two riders can't both grab the same driver. Use a transactional update with optimistic locking on driver state.

## 8. The trip state machine

A trip is a finite-state machine; transitions are the source of truth:

```
REQUESTING → MATCHED → DRIVER_EN_ROUTE → ARRIVED → IN_PROGRESS → COMPLETED
                  ↘                                              ↗
                   CANCELLED ────────────────────────────────────
```

Stored in Postgres (or DynamoDB with conditional writes). Each transition is **idempotent** keyed on trip_id + transition. Driver and rider apps poll or subscribe to status changes via WebSocket.

A great staff-level point: the trip state machine is the **anchor of correctness** — payment, ratings, dispute resolution all reference these state transitions. Make them durable, idempotent, and audit-logged.

## 9. Surge pricing

Surge is just "demand / supply heat in a region."

```
For each h3/geohash cell every 30s:
   demand  = count(ride requests in last 5 min)
   supply  = count(available drivers in cell)
   ratio   = demand / max(supply, 1)
   if ratio > threshold: surge_multiplier = f(ratio)
```

This runs as a **stream-processing job** on Kafka (Flink) consuming the location updates and ride requests. Result is published to a `surge:cell_id → multiplier` cache that the pricing service reads when quoting a fare.

Surge zones are visible to drivers (incentive to drive there) and shown to riders before they request (price transparency).

## 10. ETA computation

Two flavors:
- **Pickup ETA** (driver → rider): depends on real-time traffic + the driver's path.
- **Trip ETA** (rider's destination): same idea, longer route.

Compute via a routing service backed by:
- Static map graph (OpenStreetMap or proprietary).
- Real-time traffic — derived from anonymized speed of vehicles in each road segment (drivers themselves provide the data).
- Historical patterns by time-of-day.

For interview purposes, mention that ETA is usually a separate service (or third-party like Mapbox/Google) and that the routing graph is a graph-search problem with weighted edges. Cross-link to [Design Google Maps](/blog/system-design/design-google-maps).

## 11. Failure handling

| Failure | Behavior |
|---|---|
| **Driver app loses connection mid-trip** | Last known location stays valid for ~60s; trip continues; client reconnects and replays |
| **Matching engine crashes mid-dispatch** | Dispatch is recorded; if no driver-side ack within X seconds, retry via another worker |
| **Redis location shard down** | Read from Cassandra (slower, last-known); matching falls back to wider radius |
| **Trip DB shard down** | Affected trips can't transition; users see "service unavailable"; replay on recovery |
| **Region-wide outage** | Multi-region failover; in-flight trips are stickied to a region until completion |

## 12. The trade-offs interviewers will probe

| Question | What they want to hear |
|---|---|
| "Why geohash over S2?" | Simplicity vs accuracy; mention boundary cells |
| "Why Redis for hot store?" | 1M+ writes/sec sustainable; Cassandra is the durable backing |
| "How do you avoid double-booking?" | Atomic CAS on driver state; trip state-machine transitions |
| "How do you handle a hot prefix (downtown SF)?" | Finer geohash; replicate hot keys; in-memory quadtree on matching workers |
| "Why do drivers update every 4s, not every 1s?" | Battery + bandwidth + matching freshness trade-off |
| "How does surge work?" | Stream processor on demand/supply per cell; cached multiplier |
| "How do you scale matching to 5K matches/sec?" | Per-region matching workers; share-nothing; in-memory state |

## 13. The 30-second summary

> Ride-sharing is fundamentally a **high-write geospatial index + matching engine + trip state machine**. The interesting design is the geospatial layer (geohash/S2/quadtree, Redis hot store, Cassandra cold store), the dispatch loop (CAS on driver state, dispatch offers, accept timeouts), and the trip state machine that anchors correctness for billing and disputes. Surge is a stream-processed demand/supply ratio per cell.

Get those three layers right, with the location-update math from section 3 backing your geospatial choice, and you've answered Uber's actual interview question.
