"Design a distributed message queue" is the *premium* version of system design questions. It forces you to demonstrate fluency in **partitioning**, **replication**, **leader election**, **consumer coordination**, and **delivery semantics** — usually all in 45 minutes. This is the post I wish I'd had before my own staff-level loops.

We'll build something that looks like Kafka, but you should be able to defend every design choice from first principles, not "because Kafka does it."

## 1. Clarify before you draw

Don't sketch boxes. Ask:

- **Workload shape:** is this for high-throughput streaming (logs, events, CDC) or low-latency RPC-like jobs?
- **Ordering guarantees:** strict total order? Per-key order? None?
- **Delivery semantics:** at-most-once, at-least-once, or exactly-once?
- **Retention:** transient (delete after consumed) or durable log (replayable for days)?
- **Consumers:** one consumer per message, or fan-out to many?
- **Throughput target:** 10K msgs/sec? 1M? 10M?

For this post we'll commit to:

> Durable, replayable log. Per-key ordering. At-least-once with exactly-once *option*. Fan-out via consumer groups. Target ~1M msgs/sec, ~10ms p99 produce latency.

That single paragraph eliminates 80% of the design space. State it out loud.

## 2. Functional & non-functional requirements

**Functional:**
1. `produce(topic, key, value)` — append a message to a topic.
2. `consume(group, topic)` — read messages, advance offset.
3. `commit(group, topic, partition, offset)` — durably record progress.
4. Replay from any offset within retention.

**Non-functional:**
1. **Durability** — once acked, never lost (even on broker failure).
2. **Throughput** — 1M msgs/sec sustained per cluster.
3. **Latency** — p99 produce < 10 ms, end-to-end < 100 ms.
4. **Availability** — survive single broker, AZ, or rack failure.
5. **Per-key ordering** — messages with the same key consumed in order.

## 3. Capacity numbers (always do this)

Anchor on real numbers:

- **1M msgs/sec × 1 KB avg** → 1 GB/s ingress, 1 GB/s replication = **2 GB/s network** per broker pair.
- **7-day retention** → 1M × 1 KB × 86400 × 7 = **~600 TB raw**, **~1.8 PB with 3× replication**.
- **Per broker** at 100 MB/s sustained (NIC + disk write) → need **~10 brokers minimum**, plan for **30+ for headroom**.
- **Partitions:** ~10K per cluster is the sweet spot for ZooKeeper/KRaft-class coordination.

These numbers will be cited again and again as we make decisions.

## 4. The core abstraction: the partitioned log

The single most important idea in Kafka-class systems:

> **A topic is just a logical name for an ordered set of partitions. A partition is an append-only, segment-backed file.**

Once you internalize this, everything else falls out:

- **Ordering** is per-partition (not per-topic). To get per-key ordering, hash the key to a partition.
- **Throughput** scales linearly with partition count (each partition is independently writable to a different broker).
- **Replication** happens per-partition (each partition has a leader + N followers).
- **Consumers** parallelize by partition (a consumer group has one consumer per partition).

Almost every Kafka design choice is a consequence of this abstraction.

## 5. API design

```http
POST /produce
{
  "topic": "user-events",
  "key":   "user-42",         // optional; null → round-robin
  "value": "...binary...",
  "acks":  "all"              // 0 | 1 | "all"
}
→ 200 { "partition": 7, "offset": 1842931 }

POST /fetch
{
  "topic": "user-events",
  "group": "billing-pipeline",
  "partitions": [{ "id": 7, "offset": 1842931, "max_bytes": 1048576 }]
}
→ 200 { "records": [...], "high_water_mark": 1843200 }

POST /commit
{
  "group": "billing-pipeline",
  "offsets": [{ "topic": "user-events", "partition": 7, "offset": 1843050 }]
}
→ 204
```

Three endpoints. That's the whole user-facing surface.

## 6. The high-level architecture

```
                 ┌────────────────────┐
                 │  Metadata service  │  (ZooKeeper / KRaft / etcd)
                 │  - topic config    │
                 │  - partition →     │
                 │    leader mapping  │
                 │  - ISR sets        │
                 │  - consumer groups │
                 └─────────┬──────────┘
                           │ heartbeats / leader election
       ┌───────────────────┼───────────────────┐
       │                   │                   │
  ┌────▼────┐         ┌────▼────┐         ┌────▼────┐
  │ Broker 1│◄────────┤ Broker 2├────────►│ Broker 3│
  │  P0(L)  │  repl   │  P0(F)  │  repl   │  P0(F)  │
  │  P1(F)  │  ────►  │  P1(L)  │  ────►  │  P1(F)  │
  └────▲────┘         └────▲────┘         └────▲────┘
       │                   │                   │
       └─────producers────────────consumers────┘
```

Three layers:
1. **Metadata service** — single source of truth for topology and leadership.
2. **Brokers** — stateful storage + replication + serving.
3. **Clients** — producers and consumers; smart enough to talk to the right partition leader directly.

## 7. The write path (produce)

This is where most candidates wave their hands. Be precise:

```
1. Producer asks metadata service: "Where is the leader for topic T, partition P?"
   (Cached on the producer. Refreshed on NotLeaderForPartition error.)
2. Producer sends Produce request directly to that broker.
3. Leader broker:
   a. Appends record to active segment of partition P (sequential disk write).
   b. Updates leader_high_water_mark.
   c. Sends record to followers in the In-Sync Replica (ISR) set.
   d. Waits for follower acks based on `acks` setting:
      - acks=0:    no wait, fire-and-forget (lossy)
      - acks=1:    wait for leader's local write only
      - acks="all": wait for all ISR followers to ack
   e. Returns offset to producer.
```

<Callout type="tip" title="Why sequential append is the secret">
A modern SSD can do ~500 MB/s of *sequential* writes but only ~50 MB/s of random writes. Treating the log as append-only is what unlocks Kafka's throughput. You don't need fancy storage; you need *boring* sequential I/O on lots of cheap disks.
</Callout>

### Producer batching is mandatory

A naive producer sending one record per request will hit ~10K msgs/sec. To reach 1M msgs/sec you need:

- **Linger** — accumulate records for `linger.ms` (e.g. 5 ms) before sending.
- **Batch by partition** — one batch per partition leader.
- **Compress the batch** — LZ4 or Snappy, ~5–10× reduction on JSON.

Trade-off: latency (waiting `linger.ms`) for throughput. State this explicitly.

## 8. Replication and the ISR set

This is where senior+ candidates earn their salt. The key concepts:

- **ISR (In-Sync Replicas):** the subset of replicas that are caught up to the leader within `replica.lag.time.max.ms` (e.g. 30s).
- **High-Water Mark (HWM):** the offset up to which all ISR members have replicated. **Consumers can only read up to the HWM** — guarantees that any message they see is durable on every ISR member.
- **Leader Election:** if the leader fails, the metadata service picks a new leader from the ISR. (Picking from outside the ISR is "unclean leader election" — possible data loss.)

```
Leader   : [0..1000] HWM=998
Follower1: [0..998]  ✓ in ISR
Follower2: [0..995]  ✓ in ISR (within lag tolerance)
Follower3: [0..200]  ✗ kicked out of ISR (too far behind)
```

If the leader dies, Follower1 or Follower2 can become leader. Follower3 cannot — promoting it would lose messages 200..998.

### Replication factor decision matrix

| RF | Tolerates failures | Storage cost | Common use |
|---|---|---|---|
| 2 | 0 hardware failures (you'd lose data on any failure) | 2× | Never use in prod |
| 3 | 1 broker failure | 3× | The default. Almost always right. |
| 5 | 2 simultaneous failures | 5× | Critical pipelines, financial data |

## 9. Storage layout on a broker

Each partition lives in its own directory of segment files:

```
/data/user-events-7/
  00000000000000000000.log
  00000000000000000000.index
  00000000000000000000.timeindex
  00000000000005842731.log     ← active segment (currently being appended)
  00000000000005842731.index
  00000000000005842731.timeindex
```

- **`.log`** is the actual records, append-only.
- **`.index`** is a sparse offset → byte-position map for `O(log n)` random reads.
- **`.timeindex`** maps timestamps → offsets for time-based seeks.
- Segments roll over by size (e.g. 1 GB) or time (e.g. 7 days).
- Old segments are deleted (or compacted) when retention expires.

This layout is what lets a single broker serve millions of messages per second with predictable latency: the hot path is `mmap` + `sendfile` (zero-copy) from `.log` to socket.

### Log compaction — the alternative to deletion

For some topics (CDC streams, materialized state, config changelogs) you don't want time-based deletion. You want **the latest value per key** retained forever, and older values for the same key garbage-collected.

That's log compaction. The broker periodically rewrites a partition, keeping only the most recent record per key:

```
Before compaction:
  user:42 → "alice@a.com"   (offset 100)
  user:43 → "bob@b.com"     (offset 101)
  user:42 → "alice@new.com" (offset 200)
  user:43 → DELETE          (offset 201)
  user:42 → "alice@new2.com"(offset 300)

After compaction:
  user:43 → DELETE          (tombstone, kept until tombstone retention)
  user:42 → "alice@new2.com"(offset 300)
```

This is how Kafka backs Kafka Streams' state stores, the `__consumer_offsets` topic, and CDC pipelines like Debezium. The promise is: **a brand-new consumer reading from offset 0 will see at least the latest value for every key that ever existed**.

Two operational gotchas:
- **Tombstones** (null-value records) signal "this key was deleted." They must be retained for `delete.retention.ms` (default 24h) so consumers have time to see them.
- **Compaction is not free** — it competes with normal I/O. Run it on dedicated disk threads, off-peak.

### Tiered storage (the modern frontier)

Storing 600 TB of log on local NVMe is expensive. Newer Kafka versions (and Confluent Cloud, Warpstream, Redpanda Cloud) support **tiered storage**: hot data (last few hours) on local SSD, cold data offloaded to S3/GCS.

- Active segment writes still go to local disk → no latency penalty for producers/recent consumers.
- Closed segments are uploaded to object storage and removed from local disk.
- Consumers reading old offsets transparently fetch from object storage (slower, but rare).

This trades read latency for old data against ~10× cheaper storage. For a logs/CDC use case where consumers almost never go far back, it's a clean win. Worth a 30-second mention if the interviewer asks about cost.

## 10. The read path (consume) and consumer groups

Consumers are deceptively simple:

```
1. Consumer joins group G.
2. The group coordinator (a broker) assigns each consumer a subset of partitions.
3. Each consumer fetches its assigned partitions in parallel.
4. Periodically, consumer commits its progress (offset) to the __consumer_offsets topic.
```

Two ideas to call out:

### Consumer group rebalance

When a consumer joins or leaves the group, the coordinator runs a **rebalance**: pause everyone, recompute partition assignments, resume.

- Old protocol ("eager rebalance") stops the world.
- Modern protocol ("cooperative rebalance" / KIP-429) only reassigns the deltas.

A staff-level answer mentions this. A junior-level answer doesn't know the rebalance exists.

### Offset storage

Consumer offsets are themselves stored in a special compacted topic (`__consumer_offsets`). This is recursion done right: the system uses itself to track its own state. Mention it.

## 11. Delivery semantics — pick exactly one

| Semantic | How | Trade-off |
|---|---|---|
| **At-most-once** | Commit offset *before* processing | Crash → lose messages |
| **At-least-once** | Process *then* commit offset | Crash → reprocess (duplicate) |
| **Exactly-once** | Idempotent producer + transactional commits | Slower; needs application cooperation |

**At-least-once is the default and the right answer 90% of the time.** Make consumers idempotent (use the message key as a dedup token) and you're done.

For true exactly-once (e.g. financial pipelines):
1. **Idempotent producer** — broker dedups based on `(producer_id, sequence_number)`.
2. **Transactional commits** — `produce` and `commit_offset` happen in a single 2PC-like transaction across topics.
3. **Read isolation** — consumers only see committed records (`read_committed`).

This is how Kafka Streams does exactly-once. It's not free.

<Callout type="warn" title="The exactly-once trap">
"Exactly-once delivery" is impossible across arbitrary consumers. What's possible is **exactly-once *processing*** within a system that controls both the producer and the consumer (or where the consumer is idempotent). Be precise about this in interviews — sloppy claims here lose points fast.
</Callout>

## 12. Failure handling — the senior-level part

What happens when…

| Failure | Behavior |
|---|---|
| **Leader broker dies** | Metadata service detects via missed heartbeat (~10s). Picks new leader from ISR. Producers retry on `NotLeaderForPartition`. End-to-end blip ~10–30s. |
| **Follower broker dies** | Kicked from ISR. Leader keeps acking with the surviving ISR. When follower returns, it catches up from leader. |
| **Network partition** | If the leader is on the minority side, it can't get acks → won't advance HWM → stops accepting writes (with `acks=all`). New leader elected on majority side. |
| **Slow follower** | Kicked from ISR after `replica.lag.time.max.ms`. Doesn't block the leader. |
| **Disk full** | Broker rejects writes, alerts. Recovery is operational, not architectural. |
| **Zookeeper / KRaft outage** | Brokers keep serving with cached metadata for some time, but no leader elections, no topic creation, no consumer rebalances. Cluster degrades but doesn't crash. |

## 13. Pull vs push (a perennial interview question)

Kafka uses **pull**: consumers ask for batches. Why not push?

- **Backpressure** is automatic — slow consumer just pulls less often.
- **Batching** is simpler — consumer decides batch size, not the broker.
- **Replay** is trivial — consumer can ask for any offset; no server-side state per consumer.
- **Heterogeneous consumers** — fast and slow consumers coexist without choking the broker.

Push systems (RabbitMQ default, SQS visibility timeout) trade these for lower latency. Mention the trade-off; don't claim either is universally better.

## 14. Real-world tuning knobs — the numbers that matter

A staff-level answer mentions specific tuning parameters. Memorize the small set below; it's the difference between "I've read about Kafka" and "I've operated Kafka."

### Producer-side

| Knob | Typical value | What it does |
|---|---|---|
| `acks` | `all` | Wait for full ISR ack. `1` is faster but lossy; `0` is fire-and-forget. |
| `linger.ms` | 5–20 ms | How long the producer batches before sending. Higher = better throughput, worse latency. |
| `batch.size` | 16–64 KB | Per-partition batch size. Big batches → big compression wins. |
| `compression.type` | `lz4` or `zstd` | LZ4 is fast; zstd compresses harder at slightly higher CPU. Always compress. |
| `enable.idempotence` | `true` | Free correctness — dedups producer retries on the broker. Always on. |
| `max.in.flight.requests.per.connection` | 5 | Higher = more parallelism. Set to 1 only if you need strict ordering without idempotence. |

### Broker-side

| Knob | Typical value | What it does |
|---|---|---|
| `num.partitions` | 30–100 per topic | Drives parallelism. Hard to increase later (re-keying breaks ordering), so over-provision a bit. |
| `replication.factor` | 3 | The 99% answer. RF=2 will lose data; RF=5 wastes storage. |
| `min.insync.replicas` | 2 (with RF=3) | Quorum that must ack with `acks=all`. RF − 1 is the canonical setting. |
| `unclean.leader.election.enable` | `false` | Setting this to `true` trades availability for data loss. Almost always wrong. |
| `log.segment.bytes` | 1 GB | Segment roll-over size. Smaller = faster compaction; larger = fewer file handles. |
| `log.retention.ms` | 7 days | Time-based retention. Set per-topic for cheap. |
| `replica.lag.time.max.ms` | 30 s | How long a follower can lag before it's kicked from ISR. Too low = thrash; too high = stale ISR. |

### Consumer-side

| Knob | Typical value | What it does |
|---|---|---|
| `fetch.min.bytes` | 64–256 KB | Wait until this much is available before responding. Reduces empty fetches. |
| `fetch.max.wait.ms` | 500 ms | Cap on `fetch.min.bytes` wait. Don't hang forever on quiet topics. |
| `max.poll.records` | 500–5000 | How many messages per `poll()`. Tune for your processing latency. |
| `enable.auto.commit` | **false** | At-least-once correctness depends on you committing *after* processing. Auto-commit breaks this. |
| `session.timeout.ms` | 10–30 s | Coordinator marks consumer dead after this. Too short = false rebalances. |

### Operational sanity rules

- **Don't exceed ~10K partitions per cluster** (with old controller; KRaft pushes this much higher). Each partition is a few file handles + open mmap regions; they add up.
- **Aim for ~100 MB/s sustained per broker NIC**, not the line rate. Headroom = sanity during failover.
- **Monitor consumer lag, not throughput.** Throughput tells you the system is alive; lag tells you it's healthy. (Lag = high-water-mark − consumer offset.)
- **Don't co-locate producers and consumers** on the broker box. The broker should be doing one thing.

### KRaft vs ZooKeeper

ZooKeeper has been Kafka's metadata store since day one, but it's a separate cluster with its own ops burden. **KRaft (KIP-500)** moves metadata into Kafka itself using a built-in Raft-based log:

- Single cluster to operate, not two.
- Faster controller failover (~1 s vs 10–30 s with ZooKeeper).
- Higher partition limits (millions vs ~200K).
- Default in Kafka 3.3+; ZooKeeper removed in Kafka 4.0.

If asked "ZooKeeper or KRaft?" the right 2026 answer is **KRaft for new clusters, migrate ZooKeeper-based clusters opportunistically.** Mention KIP-500 by name if you really want the strong-hire signal.

## 15. The trade-offs interviewers will probe

| Question | What they want to hear |
|---|---|
| "Why not just use a database?" | Sequential append throughput, replay, fan-out, no contention on tail writes |
| "Why partitions instead of one big log?" | Throughput scaling, parallel consumption, but lose total order |
| "Why ISR instead of full quorum?" | Throughput — leader doesn't wait for slow replicas; tunable durability |
| "Why pull over push?" | Backpressure + replay (see above) |
| "Why mmap + sendfile?" | Zero-copy from disk → socket → 5–10× CPU reduction |
| "What if a key is super hot?" | Same partition → bottlenecked. Repartition with composite key, or accept it for ordering |
| "How do you upgrade brokers?" | Rolling restart, one broker at a time, partition leadership migrates |

## 16. What you'd build *differently* for different flavors

- **Low-latency RPC-like jobs (SQS/RabbitMQ style):** push semantics, per-message ack, visibility timeouts, no replay. Simpler, lower throughput.
- **Streaming with stream processing (Kafka + Flink):** add transactional commits + exactly-once.
- **CDC (Debezium):** add log-compaction (retain only latest value per key).
- **Pub-sub (Redis Streams, NATS JetStream):** simpler retention, often in-memory + AOF.

Mentioning these adjacent designs and *why you didn't pick them* is staff-level material.

## 17. The 30-second summary

> A distributed queue is fundamentally a **partitioned, replicated, append-only log with consumer-tracked offsets**. Throughput comes from sequential disk I/O + zero-copy reads. Durability comes from in-sync replication with a tunable acks knob. Per-key ordering comes from key-hashing to partitions. Exactly-once is a careful dance of idempotent producers + transactional commits + read isolation — not magic.

If you can land that summary at minute 40 of the interview, with the supporting depth in sections 7, 8, 11 and 12, you've given a strong-hire answer.
