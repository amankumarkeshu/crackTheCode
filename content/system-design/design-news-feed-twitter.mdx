If you do exactly one system design problem before your next interview, do this one. **News feed / Twitter timeline** is the single most-asked question across Google, Meta, Amazon, LinkedIn and Atlassian loops, and it's the one candidates most often answer at a junior level.

The issue isn't that "fan-out on write" or "fan-out on read" is hard. It's that 90% of candidates pick one and stop. The interesting answer is the **hybrid** — and you need real capacity numbers to justify it.

## 1. Clarify before you draw

Don't draw boxes. Ask:

- **Read/write ratio?** Almost always heavily skewed to reads (~100:1).
- **Timeline ordering?** Reverse chronological, or ranked/personalized?
- **Follow graph shape?** Symmetric (Facebook friends) or asymmetric (Twitter follows)?
- **Median vs max followers?** Big difference between "everyone has 200 friends" and "Cristiano Ronaldo has 600M followers."
- **Real-time?** Within 1 second? 30 seconds? Eventually?
- **Push notifications?** Out of scope for this design.

For this post we commit to:

> Twitter-style asymmetric follow graph. Reverse-chronological feed (no ranking — that's a separate ML problem). Visible within ~5 seconds. ~500M DAU. Median user follows 200, max user is followed by 600M.

## 2. Functional & non-functional requirements

**Functional:**
1. `post(user, tweet)` — create a tweet.
2. `get_feed(user, limit, cursor)` — return most recent tweets from people they follow.
3. `follow(user, target)` / `unfollow`.

Out of scope (interviewer's choice): replies, retweets, ranking, search, notifications.

**Non-functional:**
1. **Read latency:** p99 < 200 ms.
2. **Write latency:** p99 < 1 s for the poster (best-effort propagation to followers).
3. **Read throughput:** ~10× write throughput.
4. **Eventual consistency** is fine for the timeline; nobody expects realtime.
5. **High availability** for reads. Outages are world news.

## 3. Capacity numbers (everything hinges on these)

- **500M DAU**, average user reads feed 5×/day → **2.5B feed reads/day** ≈ **30K reads/sec average, ~300K peak**.
- **Posts:** 500M DAU × 0.4 posts/day = **200M posts/day** ≈ **2.3K writes/sec average, ~25K peak**.
- **Follow graph:** 500M users × 200 follows median = **100B follow edges**. Even at 16 bytes each = **1.6 TB** for the graph alone.
- **Tweet storage:** 200M × 365 × 5 yrs × 500 bytes = **180 TB raw**, ~**500 TB with replication**.
- **Read amplification per post (fan-out on write):** 200M posts × 200 followers = **40B writes/day** to inboxes — 10× the post rate. Manageable.
- **Read amplification for a celebrity (600M followers):** 1 post = 600M inbox writes. **Catastrophic** if naive.

The celebrity number alone tells you fan-out-on-write *cannot* be the whole answer. We need a hybrid.

## 4. API design

```http
POST /tweets
{ "userId": "u_42", "text": "...", "mediaIds": [] }
→ 201 { "tweetId": "t_91283412", "createdAt": "2026-05-06T07:30:00Z" }

GET /feed?cursor=...
→ 200 {
    "tweets": [{...}, {...}],
    "nextCursor": "..."
  }

POST /follow { "targetUserId": "u_99" } → 204
```

Cursor-based pagination only — never offset-based. Offset-based at this scale is a death sentence (you can't `OFFSET 100000` cheaply).

## 5. The two pure approaches

### Fan-out on write ("push")

When user A posts, write that tweet's ID into the inbox/timeline of every follower of A.

```
A posts t1
  → for each follower F of A:
      INSERT INTO timeline(user=F, tweet_id=t1, ts=now)
A's followers later GET feed:
  → SELECT tweet_id FROM timeline WHERE user=F ORDER BY ts DESC LIMIT 50
```

- **Pros:** Reads are dirt cheap — one indexed range scan on a single user's timeline.
- **Cons:** Writes are expensive (200× amplification on average; **600M× for a celebrity**).
- **Verdict:** Great for normal users. Catastrophic for celebrities.

### Fan-out on read ("pull")

When user F asks for their feed, fetch the last N tweets from each followee, merge.

```
F GETs feed:
  → followees = SELECT followee_id FROM follows WHERE follower=F
  → for each followee:
       fetch their recent tweets
  → merge sort by timestamp, return top 50
```

- **Pros:** Cheap writes (1 row inserted, period).
- **Cons:** Reads are expensive — 200 followee fetches per feed read, with sort/merge.
- **Verdict:** Great for celebrities (their tweets aren't pre-fanned-out). Bad for normal users on every read.

## 6. The hybrid (the answer they want)

The real Twitter design (publicly described in their architecture talks) is:

> **Fan-out on write for normal users; pull-on-read for celebrity tweets; merge at read time.**

```
On post:
  if author is "celebrity" (followers > 100K):
      do NOT fan out. Just store in timeline_authors table.
  else:
      fan out to all followers' inbox tables.

On read:
  fetched_tweets = read from F's pre-built inbox          ← normal followees, cheap
  + read recent tweets from each celebrity F follows      ← small N, manual merge
  → merge sort by timestamp, return top 50.
```

This is the *strong-hire* answer. The interviewer is waiting for it. Two specific things to call out:

### Why this works

- **99.9% of users have < 1000 followers.** Fan-out on write is cheap for them.
- **A tiny number of accounts have millions of followers.** Pull-on-read keeps them from bringing the system down.
- **Followers of a normal user only see their inbox** (1 query). Followers of a celebrity pay a small extra cost (N celebrity-fetches at read time). Both stay fast.

### The threshold matters

- Threshold too low (e.g. 1000 followers) → too many "celebrities," reads get heavy.
- Threshold too high (e.g. 10M) → fan-out storms still happen for accounts in the 100K–10M range.
- Real-world tuning: **somewhere around 100K–1M followers**, often dynamic per user activity.

<Callout type="tip" title="Land the threshold conversation">
When you propose the hybrid, immediately say: "The interesting question is *where* to put the celebrity threshold." That single sentence shows you've thought beyond the textbook answer.
</Callout>

## 7. Data model

```sql
-- Users (sharded by user_id hash)
users(user_id PK, name, follower_count, ...)

-- Tweets (sharded by tweet_id range or hash)
tweets(tweet_id PK, author_id, text, media_ids[], created_at)

-- Follow graph (sharded by follower_id; reverse-index needed for "who follows me")
follows(follower_id, followee_id, created_at, PK(follower_id, followee_id))
follows_reverse(followee_id, follower_id, created_at, PK(followee_id, follower_id))

-- Inbox / pre-built timelines (sharded by user_id)
timeline(user_id, tweet_id, author_id, ts, PK(user_id, ts DESC))
   ↳ Capped at, say, 800 entries per user (rotate out the oldest).

-- Author timelines (for pull-on-read of celebrities)
timeline_authors(author_id, tweet_id, created_at, PK(author_id, created_at DESC))
```

Two sharding decisions worth defending:

- **`tweets` sharded by `tweet_id`** (Snowflake-style ID with timestamp prefix → roughly time-ordered shards, easy hot-shard rotation).
- **`timeline` sharded by `user_id`** so all of a user's inbox lives on one shard. Critical: feed reads are then a single-shard query.

For the storage system itself: a wide-column store (Cassandra, ScyllaDB, DynamoDB) is canonical because:
- Append-heavy.
- Per-user time-ordered range scans.
- No joins.
- Easy multi-region replication.

### Snowflake ID anatomy (use this exact answer when asked)

Tweet IDs are not random — they're carefully designed to be **sortable, sharded, and globally unique without a central sequence**. The 64-bit layout Twitter actually used:

```
 1 bit | 41 bits                    | 10 bits     | 12 bits
 sign  | timestamp ms since epoch   | machine ID  | sequence within ms
       | (custom epoch, e.g. 2010)  |             |
```

Why each field is the size it is:

- **41-bit timestamp** → 2^41 ms ≈ **69 years** before rollover. Custom epoch (start counting from your launch year, not 1970) buys you another 40 years of headroom.
- **10-bit machine ID** → 1024 distinct ID-generator nodes. Plenty for any single deployment.
- **12-bit sequence** → 4096 IDs per ms per machine = 4M IDs/sec per machine. Aggregate well over 1B/sec across the fleet.

Wins:
- Sorted by ID = sorted by time → range queries on `tweet_id` are cheap.
- No central sequence service → no SPOF, no single-node bottleneck.
- The high bits encode time → range-sharded `tweets` table naturally rotates hot shards over time.

Trade-offs:
- IDs are **predictable** (the next tweet's ID is roughly your_id + small_delta) → enumeration attacks possible. Insert randomness in low bits if that matters.
- Clock skew is correctness-critical (see the [URL Shortener post](/blog/system-design/design-url-shortener) for the full clock-skew trap).

Drop "Snowflake-style 64-bit ID with a custom epoch and per-machine sequence" in the interview. It signals *operational* familiarity, not just a Wikipedia read.

## 8. The write path (fan-out)

```
1. User posts → API gateway → Tweet Service
2. Tweet Service:
   a. Generate tweet_id (Snowflake — embeds timestamp, sortable, unique).
   b. Write to tweets table (durable).
   c. Write to timeline_authors[author_id].
   d. Publish to Kafka topic "tweet.created" → return 201 to user.
3. Async Fan-out Worker (Kafka consumer):
   a. If author.follower_count > THRESHOLD (celebrity): do nothing.
   b. Else: read followers list (paginated), for each follower
      INSERT INTO timeline(follower_id, tweet_id, author_id, ts)
   c. Use bulk inserts (1000 rows per batch).
```

Latency to the poster: just the tweet write (~tens of ms). Followers see it within seconds via async fan-out.

### The celebrity follower-fetch problem

Even *just listing* the 600M followers of a celebrity is slow. Fix:
- **Don't paginate at fan-out time** — celebrities are skipped entirely. ✓
- **For everyone else,** paginate the follower list and parallelize across worker shards.

## 9. The read path

```
1. GET /feed → API gateway → Feed Service
2. Feed Service:
   a. Cache check: timeline:{user_id} in Redis? Return.
   b. SELECT tweet_id, author_id, ts FROM timeline WHERE user=F LIMIT 50  ← inbox reads
   c. SELECT followee_id FROM follows WHERE follower=F AND follower_count>THRESHOLD
                                                    ← celebrity followees only
   d. For each celebrity:
       SELECT tweet_id, ts FROM timeline_authors WHERE author=C
                                              AND ts > F.last_feed_read
                                              ORDER BY ts DESC LIMIT 50
   e. Merge step (b) and (d) by ts, dedupe, take top 50.
   f. For top 50: bulk SELECT tweets WHERE tweet_id IN (...)  ← hydrate
   g. Cache result, return.
```

The cache step is non-negotiable. **Without caching, the merge in step (e) repeats on every scroll** — death.

### Inbox vs hydrated cache

Two cache layers, often:
- **Timeline cache:** ordered list of tweet IDs only. Updated on fan-out.
- **Tweet cache:** tweet_id → full tweet object. Hot tweets stay here forever.

This separation lets you invalidate one without the other. A tweet edit invalidates the *tweet* cache but leaves the *timeline* (ID list) untouched.

## 10. Capping and storage management

You don't keep an infinite inbox per user. Cap it (e.g. 800 entries):

- After 800, oldest entries roll off.
- Reads beyond 800 fall back to fan-out-on-read of all followees (for the rare deep-scroll user).
- This caps inbox storage at `500M users × 800 entries × 16 bytes = 6.4 TB` — manageable.

## 11. Pre-warming on follow

When user F follows user A:
1. Insert into `follows`.
2. Optional: backfill F's inbox with A's last 50 tweets so F's feed isn't empty.
3. Update A's `follower_count`. If it crosses the celebrity threshold, A's future tweets stop fanning out.

The backfill step is an extra write but vastly improves new-user experience. Worth mentioning.

## 12. The celebrity demotion / promotion problem

What if a normal user becomes a celebrity (follower count crosses threshold)?

- **Going up (normal → celebrity):** future tweets stop fanning out. Existing inbox entries stay; they'll roll off naturally.
- **Going down (celebrity → normal, e.g. mass unfollow):** future tweets start fanning out again. No backfill — old tweets stay celebrity-style.

Both transitions are essentially free. Easy to defend.

## 13. Failure handling

| Failure | Behavior |
|---|---|
| **Fan-out worker dies mid-job** | Kafka offset not committed → another worker picks up. Idempotent inserts (PK = `(user_id, tweet_id)`) prevent duplicates. |
| **Tweet write succeeds, fan-out fails forever** | Followers eventually see the tweet via pull-on-read for celebrities, or via deep-scroll fallback. Never silently dropped. |
| **Timeline cache cold** | Fall back to DB. Slower but correct. |
| **DB shard down** | Affected users see stale feeds; new tweets queue in Kafka and replay when shard returns. |
| **Whole region down** | Multi-region replication; read-only mode in failover region. |

## 14. Ranking layer — from time-ordered candidates to ML-scored feed

We've designed a **chronological** feed. But every modern social product (Twitter Home, Instagram, TikTok, LinkedIn) ranks instead. The interviewer will *almost always* ask: "How would you add ranking?"

The right answer is a clean separation of concerns:

```
┌─────────────────────┐  ┌──────────────────┐  ┌───────────────────┐
│ Candidate generation│→ │  Feature fetch   │→ │  Scoring (ML)     │ → top K
│ (this entire post)  │  │ (user/item embed)│  │ (DNN / GBDT)      │   shown
└─────────────────────┘  └──────────────────┘  └───────────────────┘
        ~5,000                  ~5,000              ~50 → 10
        candidates              enriched            best
```

### Stage 1 — Candidate generation (what we already built)

Pull the last few hundred tweets from the user's pre-built inbox + the last few celebrity tweets. **Don't rank yet** — just produce ~5,000 candidates per feed request. Latency budget: ~50 ms.

This is where everything we designed up to section 13 lives. Ranking sits *on top*.

### Stage 2 — Feature hydration

For each candidate tweet, fetch:
- **Item features** — author engagement rate, recency, media type, language, predicted topic.
- **User features** — viewer's interest embedding, time of day, device, recent dwell-time history.
- **Cross features** — past interactions between viewer and author, shared social graph, prior session signals.

This is bulk lookups against feature stores (e.g. Feast, Tecton, or Redis with embeddings). Latency budget: ~30 ms via parallel fetches.

### Stage 3 — Scoring

A model — typically a deep neural network or GBDT for online speed — produces a score per (viewer, candidate). Top K go into the feed.

Pragmatic patterns:
- **Two-tower model** for fast scoring: precompute viewer embedding once per session; precompute candidate embeddings offline; online step is a dot product. Sub-ms per item.
- **Multi-objective scoring**: predict P(like), P(reply), P(retweet), P(dwell time > 3s) — combine via a learned weighting. This is closer to what Twitter actually does (see the open-sourced "the-algorithm" repo).
- **Real-time signal injection**: if the viewer scrolls past a tweet without engaging in the last 5 minutes, downrank similar tweets immediately.

### Stage 4 — Filtering / business rules

After scoring but before serving:
- Remove tweets the viewer has already seen (per-viewer Bloom filter of seen IDs).
- Apply blocklist / muted-words filter.
- Apply policy filter (NSFW gates, regulatory restrictions).
- Cap diversity (don't show 5 tweets from the same author).

### Latency budget breakdown

| Stage | Budget |
|---|---|
| Candidate generation | 50 ms |
| Feature hydration | 30 ms |
| Scoring (top-K) | 20 ms |
| Filtering + serialization | 20 ms |
| Network in/out | 30 ms |
| **Total p99** | **~150 ms** |

### Cold-start: a new user has no signal

A brand-new user has no inbox, no follows, no embedding. Three fallbacks:

1. **Popular-content fallback** — global trending tweets, regionally weighted.
2. **Onboarding interest selection** — ask the user to pick 5 topics on signup; bootstrap the feed from those topic streams.
3. **Friend-of-friend / address-book** — cold inbox seeded from people whom *this user's recent contacts* follow.

Almost every social product runs all three in parallel for the first session and uses the engagement signals to bootstrap real personalization within a day.

### What separates a senior answer from a staff answer

Junior answer: "We'd add an ML model that scores tweets."

Staff answer: "Ranking is a separate offline-trained-online-served pipeline. We'd keep our chronological design intact for candidate generation, hydrate features in parallel against a feature store, and score with a two-tower model that lets us precompute viewer embeddings once per session. Cold-start uses three fallbacks. The whole layer adds ~70 ms p99 to feed reads. We'd A/B test the new ranker with a holdback population for at least two weeks before full rollout."

Land that and you've answered the staff version of the most-asked system design question.

## 15. The trade-offs interviewers will probe

| Question | What they want to hear |
|---|---|
| "Why hybrid instead of pure push or pure pull?" | The celebrity problem — show numbers |
| "Why a Snowflake ID for tweets?" | Sortable, sharded, unique, no central sequence |
| "Why cap the inbox?" | Storage bound; deep-scroll falls back to pull |
| "What if a celebrity tweets and immediately deletes?" | Need a delete-fanout — or filter at read time via a small "deleted" set |
| "How do you order by 'most relevant' instead of time?" | That's a scoring / ML layer on top of the time-ordered candidate set |
| "How do you handle replies and retweets?" | Treat retweets as new tweets with a `referenced_id`; hydrate at read time |
| "Why not just use Postgres?" | Write amplification of fan-out; Cassandra/Dynamo handle the time-ordered append pattern natively |

## 16. What changes for Facebook (symmetric friends)

- Smaller fan-out (median ~300 friends, not unbounded followers) → fan-out on write works for almost everyone.
- Heavier ranking (Facebook actually orders by ML score) → the candidate-fetch is the same; the *score-and-sort* layer is a separate service.
- More privacy filters (post visibility settings) → applied at read time on the candidate set.

## 17. The 30-second summary

> News feed is fundamentally a **fan-out problem**. Pure push fails at the celebrity tail; pure pull fails on the common case. The right answer is **hybrid: push for normal users, pull for celebrities, merge at read time**. Storage is a wide-column store sharded by user_id for inboxes and by tweet_id for content. Caching is non-optional. Capacity numbers (200 follower median vs 600M celebrity max) drive every architectural choice.

Land that summary in minute 40, with the specific math from section 3 backing your hybrid choice, and you've given a staff-level answer to the most-asked system design question of the decade.
