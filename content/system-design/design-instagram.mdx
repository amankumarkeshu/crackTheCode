Instagram is mostly **News Feed + WhatsApp + YouTube** stitched together with photo-specific tweaks. If you've already designed those (we have), this question is about identifying which patterns you reuse and which subsystems are truly unique. The unique parts: the **photo upload pipeline**, **Stories** (different storage strategy), and **Explore** (interest-based ranking, not graph-based).

## 1. Clarify before you draw

- **Scope?** Photos only, or videos and Reels?
- **Feed scale?** ~2B users, asymmetric follows.
- **Stories?** Yes — 24-hour ephemeral.
- **Direct messages?** (Cross-link to chat.)
- **Explore / discovery?** Yes — interest-based, not just from people you follow.

For this post: photos + short videos, full feed + stories + explore, 2B MAU, 100M+ posts/day.

## 2. Capacity numbers

- 100M posts/day, avg 1 photo each, ~3 MB compressed → **~300 TB/day raw**.
- After multi-resolution generation (4 sizes per photo) → **~600 TB/day**.
- Reads: ~5B feed reads/day at avg 30 photos viewed = **150B image fetches/day** = ~1.7M reads/sec average. CDN does ~99%.
- Stories: 500M stories/day, 24h TTL → ephemeral, never enters long-term storage.

## 3. Architecture overview

```
Mobile App ─► API Gateway ─► Service Mesh ─►
   ┌──────────────────────────────────────────────┐
   │ Posts Service     Media Pipeline             │
   │ Feed Service      Object Storage + CDN       │
   │ Stories Service   Notification Service       │
   │ DM Service        Explore Service (ML)       │
   │ User Service      Search Service             │
   └──────────────────────────────────────────────┘
```

Each service owns its data and exposes APIs. Cross-service comms via gRPC.

## 4. Photo upload pipeline

```
1. Client → API: pre-upload, gets pre-signed URL.
2. Client → Object Storage: PUTs original (chunked for big files).
3. Client → API: CommitPost(post_id, original_blob_id, caption, ...).
4. Posts Service:
   a. Persists post row (status: PROCESSING).
   b. Publishes "media.uploaded" to Kafka.
5. Media workers:
   a. Generate 4 sizes (150x150 thumb, 320x320, 720x720, 1080x1080).
   b. Strip EXIF.
   c. Optionally re-encode to AVIF/WebP for size.
   d. Run safety classifier (ML model for NSFW / hate / spam).
   e. Write all variants to object storage.
6. Posts Service marks post READY → triggers fan-out to followers' feeds.
7. CDN-pre-warm: push the smallest 2 variants to top regions.
```

Why pre-generate vs on-the-fly? **At Instagram scale, pre-generation wins** by orders of magnitude on CDN cache hit rate and origin CPU. On-the-fly resize is great for bespoke workloads, terrible for 2B users.

## 5. The feed — reuse News Feed

Instagram's home feed is the **hybrid push/pull** described in [News Feed (Twitter)](/blog/system-design/design-news-feed-twitter):
- Normal users (median ~150 follows) → fan-out on write to followers' inboxes.
- Mega-celebrity (Cristiano Ronaldo, 600M followers) → pull at read time.
- Inbox capped at ~500 entries; deep-scroll falls back to pull.

The major Instagram-specific difference: **the feed is ranked, not chronological** since 2016. So the inbox stores *candidates* (post IDs); a ranking layer produces the actual viewing order at read time. See section 9.

## 6. Stories — different storage rules

Stories are **24-hour ephemeral** — fundamentally different from posts:

```sql
stories(
  id           bigint PK,
  user_id      bigint,
  media_url    text,
  created_at   timestamp,
  expires_at   timestamp,           -- created_at + 24h
  view_count   bigint
)
```

- TTL'd index: don't return rows with `expires_at < now()`.
- A nightly GC job deletes the underlying media from object storage.
- Stories are **fan-out on read** — when you open the app, Instagram queries "stories from people I follow where expires_at > now()." No inbox table.

Why different from feed?
- Volume: Stories volume is huge but lifetime is tiny → fan-out-on-write would be all wasted writes.
- Read pattern: viewers explicitly scroll the stories tray; not interleaved with feed.
- Engagement: most stories are viewed within hours of posting → cache-friendly hot set.

This contrast is a great staff-level point: same product, two completely different storage strategies based on data lifetime and access pattern.

## 7. Explore — the discovery system

The "Explore" tab shows posts from people you *don't* follow but might like. Pure ranking problem:

```
1. Candidate generation (offline, refreshed hourly):
   For each user, produce top ~5K candidate posts based on:
     - Their follow graph (friends-of-friends)
     - Topic / interest embeddings
     - Geographic affinity
     - Trending in their language

2. Online scoring (per request):
   Fetch the user's current candidate set
   Score each candidate with a neural network
   Filter (already-seen, blocked authors, NSFW)
   Return top 20 to the client

3. Real-time updates:
   When user engages (like, save, dwell time), update their interest embedding
   in a fast cache; next request uses fresh signal.
```

Same pattern as the feed ranking layer in [News Feed (Twitter)](/blog/system-design/design-news-feed-twitter#14-ranking-layer-from-time-ordered-candidates-to-ml-scored-feed).

## 8. Like counts, view counts, follower counts

These are **distributed counters** (huge write rate, eventually consistent). See [Design a Distributed Counter](/blog/system-design/design-distributed-counter).

Common pattern: each counter is sharded into N sub-counters; reads sum across shards, writes go to a random shard. Hot posts (a Beyoncé post) go into a special "celebrity-counter" tier with even more shards.

## 9. Direct Messages

Reuse the [WhatsApp / Chat](/blog/system-design/design-whatsapp-chat) design wholesale. Instagram DM is essentially Messenger — long-lived connections, per-conversation sharded log, presence layer.

## 10. CDN strategy

Same multi-tier CDN as YouTube:
- Edge caches in ISPs.
- Photo URLs are content-hashed → `https://cdn.ig/p/<hash>/<size>.webp` → infinitely cacheable, no invalidation needed.
- A "deleted" photo is removed from object storage; CDN edges expire it within hours via TTL.

## 11. Failure handling

| Failure | Behavior |
|---|---|
| **Upload fails mid-photo** | Resumable upload retries failed chunks |
| **Media worker crashes** | Kafka-backed job; another worker reprocesses |
| **CDN cache miss spike** | Origin scales out; pre-warm hot content |
| **Feed inbox shard down** | Fall back to fan-out-on-read; user sees fewer posts but no error |
| **DM connection server crash** | Reuse WhatsApp's reconnect-via-session-registry |

## 12. The trade-offs interviewers will probe

| Question | What they want to hear |
|---|---|
| "How is this different from Twitter?" | Photos, ranked feed, ephemeral Stories, Explore |
| "Why pre-generate sizes vs on-the-fly?" | Cache hit rate at 1.7M reads/sec |
| "Why Stories don't fan out on write?" | 24h lifetime + read-pattern differences |
| "How does Explore work without a follow graph?" | Interest embeddings + candidate gen + ML scoring |
| "How do you scale like-counts on a viral post?" | Sharded counters; celebrity tier with extra shards |
| "How do you handle deleted photos?" | Object storage delete + CDN TTL; never purge edges manually |
| "How do you serve content to 2B globally with low latency?" | Multi-tier CDN; content-hashed URLs; pre-warm trending |

## 13. The 30-second summary

> Instagram is **News Feed (with ranking) + Chat + YouTube** with photo-specific tweaks. The unique parts: a multi-resolution upload pipeline driven by Kafka, Stories with fundamentally different storage (TTL'd, fan-out-on-read), and an Explore page that's pure ML ranking with no follow-graph dependency. Like-counts are distributed counters; everything is content-hashed for infinite CDN cacheability.

Land that, and the celebrity-vs-normal-user dichotomy from the feed (and now the *Stories ephemeral* contrast), and you've answered the staff version of this question.
