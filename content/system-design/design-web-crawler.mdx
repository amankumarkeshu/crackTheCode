"Design a web crawler" is one of those questions that sounds easy ("for url in urls: fetch(url)") and is brutally hard once you actually think about scale. The Internet has ~50B+ pages; you have to fetch them respectfully, dedup them, parse them, and feed downstream systems, all without getting banned.

## 1. Clarify before you draw

- **Scope?** General web (Googlebot), single domain (e.g. e-commerce price tracker), focused (news only)?
- **Refresh rate?** Crawl every page once a month? Hot pages every hour?
- **Volume?** 1B URLs, 50B URLs?
- **What downstream consumes it?** Search index, archive, ML training data, link-checker?
- **Politeness?** Honor `robots.txt`, rate-limit per domain?

For this post: general web, ~10B pages target, monthly recrawl for cold + hourly for hot, search-index downstream, full politeness.

## 2. Functional & non-functional requirements

**Functional:**
1. Fetch HTML pages from seed URLs.
2. Extract new links → enqueue.
3. Dedup URLs (don't re-crawl).
4. Dedup content (don't re-store identical pages).
5. Honor `robots.txt` and per-domain rate limits.

**Non-functional:**
1. **High throughput**, sustained 10K+ pages/sec.
2. **Politeness**, never overload a single host.
3. **Fault-tolerant**, workers die routinely.
4. **Extensible**, extract new metadata without redesigning the pipeline.

## 3. Capacity numbers

- 10B pages at avg 100 KB each = **~1 PB raw HTML**. Compressed (gzip ~5×) = ~200 TB.
- Crawl 10B over 30 days = **~4K pages/sec sustained**.
- URL frontier holds many billions of URLs in flight or queued; ~30 GB even at 30 bytes/URL.
- DNS lookups: 10K/sec without caching is a problem; with caching, 100/sec.

## 4. The pipeline

```
Seed URLs ──► URL Frontier (priority queue per host)
                  │
                  ▼
           DNS Resolver (cached)
                  │
                  ▼
           Fetcher Worker pool ─► HTTP Fetch ─► Raw HTML store (object storage)
                  │
                  ▼
           Parser Worker pool ─► Extract links + content
                  │       └─► Content dedup (SimHash)
                  ▼
           URL extractor ─► Filter ─► back to URL Frontier
                  │
                  ▼
           Indexer downstream
```

Each box is independently scaled. The hard ones: URL frontier and dedup.

## 5. The URL frontier (the heart of the crawler)

Two requirements that fight each other:
- **High throughput**, pull 10K URLs/sec to fetch.
- **Politeness**, never have more than 1 in-flight request per host.

Single FIFO queue won't work, you'd hammer popular hosts.

### Multi-queue frontier (Mercator design)

```
Host A queue: [url1, url2, url3, ...]
Host B queue: [url10, url11, ...]
Host C queue: [url20, ...]
```

Workers pick a host, take one URL, fetch, then **wait `crawl_delay` ms before this host is eligible again**. A small dispatcher keeps a heap of "next-eligible host" times.

```
class HostScheduler:
    next_eligible: PriorityQueue[(when_unlocked, host)]

    def pick():
        when, host = next_eligible.peek()
        if when > now(): sleep(when - now())
        url = host_queue[host].pop()
        return url, host

    def release(host, crawl_delay_ms):
        next_eligible.push((now() + crawl_delay_ms, host))
```

Distributed: shard host queues by `hash(host)` so all URLs for `example.com` go to the same worker, naturally enforcing the per-host limit.

### Priority within frontier

Not all URLs are equal:
- High priority: news sites, frequently-updated, high-PageRank.
- Low priority: deep PDF archives, low-traffic pages.

Use multiple priority bands per host queue; workers pull from the highest non-empty band first.

## 6. URL deduplication at scale

Trillions of URLs. Naive `Set[str]` won't fit in memory.

### Bloom filter (the right answer)

A Bloom filter of "URLs we've seen" with target false-positive rate ~1%:

- 10B URLs at 1% FPR → **~12 GB Bloom filter** (about 1.2 bytes per URL with 7 hash functions).
- Adding a URL: O(k) hashes.
- Check: O(k) hashes; if "no" → definitely new; if "yes" → probably seen, optionally double-check against the durable store.

**Trade-off:** false positives mean you might *miss* crawling a small % of URLs. Acceptable for general web; not for a price tracker that needs every URL.

For zero false-positives: write each URL to a sharded KV store (key = url_hash) and check there. ~10× more network/disk than a Bloom filter.

### Canonicalization first

Before hashing/inserting:
- Lowercase the host.
- Drop tracking params (`utm_*`, `gclid`, etc.).
- Normalize path (`/foo/` → `/foo`).
- Handle session IDs and `#fragment` (drop fragment).

Skipping canonicalization makes your dedup useless, `example.com/x` and `EXAMPLE.com/x` look different.

## 7. Content deduplication

Different URLs may serve identical content (mirrors, syndication, scraper sites). Storing and indexing each is wasteful.

### Exact match: hash the body
SHA-256 of the HTML → KV. Cheap, but misses near-duplicates.

### Near-duplicate: SimHash / MinHash

- **SimHash:** 64-bit fingerprint where Hamming distance ≈ content similarity. "Same article, different ads" → distance &lt; 3.
- **MinHash + LSH (Locality-Sensitive Hashing):** for finding "documents that share &gt; 80% of shingles."

Build pipeline: hash → store in fingerprint index → if distance to any existing fingerprint &lt; threshold, mark as duplicate (drop or link to canonical).

This is what de-duplicates the search index.

## 8. DNS caching

10K fetches/sec, 1 DNS lookup per host = thousands of DNS queries/sec to your resolver. Real DNS will rate-limit you.

Solution:
- Per-worker LRU DNS cache, TTL = the response's TTL.
- Run **your own recursive resolver** (Unbound, BIND) in front of upstream. Caches aggressively.
- For very large crawls: pre-resolve the top N hosts at startup.

## 9. Politeness, the part that gets you sued

Beyond per-host concurrency:

- **`robots.txt`**, fetch and cache per-host (24h TTL). Honor `Disallow` and `Crawl-Delay` directives. Most major crawlers also honor `Allow` and pattern wildcards.
- **`<meta name="robots" content="noindex">`**, skip indexing.
- **`User-Agent`**, set a clear one with a contact URL: `MyCrawler/1.0 (+https://mycompany.com/crawler)`. Some sites block unidentified crawlers.
- **Backoff** on 5xx and 429 responses; never hammer a struggling site.
- **Sitemaps**, when available, prefer URLs from `sitemap.xml` over discovery via link extraction.

## 10. Failure handling

| Failure | Behavior |
|---|---|
| **Fetcher crashes mid-page** | URL goes back into frontier; retry with backoff |
| **HTTP 5xx / timeout** | Backoff exponentially; retire after N attempts |
| **HTTP 4xx** | Don't retry; record and move on |
| **Parser dies on weird HTML** | Catch, log, continue; don't lose the queue position |
| **Dedup store unavailable** | Optionally fail-open (re-crawl) or pause that host queue |

## 11. Storage layout

```
raw_html/<crawled_at>/<url_hash>.html.gz       (object storage)
fingerprints/         simhash → url_hash       (KV / Redis)
url_seen_bloom        Bloom filter             (sharded by url prefix)
robots_cache/host    → robots.txt + parsed     (cache w/ TTL)
host_metadata/host   → last_crawled, fetch_stats, courtesy_factor
```

Raw HTML in object storage is canonical. Everything else is index / cache that can be rebuilt.

## 12. The trade-offs interviewers will probe

| Question | What they want to hear |
|---|---|
| "Why a Bloom filter for URL dedup?" | Memory savings; bounded false positive |
| "Why SimHash for content dedup?" | Catches near-duplicates that exact hash misses |
| "How do you maintain politeness across many workers?" | Shard frontier by host; per-host scheduler |
| "Why DNS caching?" | Otherwise DNS is your bottleneck |
| "How do you crawl JS-heavy sites?" | Headless browser pool (Chrome/Puppeteer); 100× more expensive than HTML fetch; use sparingly |
| "How would you re-crawl?" | Per-URL `next_crawl_at` based on change frequency; high-traffic pages re-crawled hourly |
| "What about traps (infinite calendars, query-param explosions)?" | Per-host URL limit; depth limit; URL pattern blocklists |

## 13. The 30-second summary

> A web crawler is fundamentally a **multi-queue URL frontier with per-host politeness, a Bloom-filter dedup layer for URLs, a SimHash dedup layer for content, and an aggressive DNS cache**. The hard parts aren't fetching, they're frontier scheduling, dedup at scale, and not getting banned. Real crawlers are 80% queue management and 20% HTTP.

Land that with the host-scheduler design from section 5 and the dedup math from section 6, and you've answered the senior version of this question.
