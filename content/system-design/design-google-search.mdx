"Design Google Search" is the most-asked search question because it covers the whole pipeline: **crawl → index → serve → rank**, each with its own scaling story. You won't out-Google Google in 45 minutes, but a staff candidate must show the moving parts and the fundamental trade-offs.

## 1. Clarify before you draw

- **Web search** (this post) or just our internal docs?
- **Document scale?** ~100B documents, growing.
- **Query QPS?** ~100K (Google scale; smaller for typical interview).
- **Latency target?** Median ~300 ms, P99 ~1 sec.
- **Result quality?** Ranked list, top 10 results matter most.
- **Personalization?** User history affects ranking?
- **Vertical search?** Images, news, videos? (Out of scope here, focus on web.)

## 2. Functional & non-functional requirements

**Functional:**
1. User enters query → top-K ranked results.
2. Document discovery (crawl).
3. Indexing (build inverted index).
4. Query parsing (typo correction, language detection).
5. Snippet generation per result.

**Non-functional:**
1. **Low query latency**, sub-300 ms median.
2. **High freshness**, news in seconds, regular pages in hours-days.
3. **High availability**, Google.com 99.999%.
4. **Massive scale**, 100B documents, 100K QPS.

## 3. The big four sub-systems

```
Crawler ──► Indexer ──► Index Server ──► Query Server
   ▲                         (sharded)         ▲
   │                                            │
URL frontier                                User query
(seed list)
```

Each is its own service with its own scaling regime. Reuse much of [Design a Web Crawler](/blog/system-design/design-web-crawler) for the crawl piece, focus this post on **indexing and serving**.

## 4. Capacity numbers

- 100B docs × 5 KB body avg = **500 PB raw** (compressed: ~100 PB).
- Inverted index: ~10 PB (text only; with positional data more).
- Doc store (for snippet generation): ~150 PB.
- Index serving fleet: thousands of shards, each ~10–100 GB on SSD.
- Query path: each query touches all shards in parallel, **massive scatter-gather**.

## 5. The inverted index: heart of the system

A forward index says: `doc_5 → ["the", "quick", "brown", "fox"]`. Useless for search.
An **inverted index** says: `"fox" → [doc_5, doc_42, doc_999, ...]`. The lookup table for queries.

For "best pizza near me":
1. Lookup `best` → posting list of doc IDs.
2. Lookup `pizza` → posting list.
3. Lookup `near` → posting list.
4. Intersect (AND): docs matching all three.
5. Rank by score; return top-K.

### Posting list entries
Beyond the doc ID, each entry stores:
- **Term frequency** in the document.
- **Position(s)** of the term, for phrase queries `"best pizza"` (must appear adjacent).
- **Field** (title, body, anchor text), title matches outweigh body matches.

### Compression
Posting lists are huge. Use **delta encoding + variable-byte coding** (e.g. `[42, 47, 51]` → `[42, 5, 4]` → fewer bytes). Posting lists compress 5–10×.

## 6. Sharding the index

100B docs × posting lists won't fit on one machine. Two sharding axes:

### Term-sharded (a.k.a. global index)
Each term's full posting list lives on one shard.
- Pro: query for term `pizza` hits one shard.
- Con: hot terms (`the`, `best`) overload one node; multi-term queries scatter.

### Doc-sharded (a.k.a. local index, what Google uses)
Each shard owns ~1/N of all documents and has a *local* inverted index over those.
- Pro: load balanced, every shard sees roughly equal traffic.
- Pro: easy to add shards as the corpus grows.
- Con: every query hits **every shard** in parallel.

**Default: doc-sharded.** Despite the scatter, it's the only design that scales linearly with corpus size. Google's index has thousands of shards.

## 7. Query path (the scatter-gather)

```
Query: "best pizza in Berlin"
       │
       ▼
  Query Parser ─── tokenize, spell-correct, language ID, intent classification
       │
       ▼
  Mixer / Front-end
       │
   ┌───┼───┐                ┌── replicas of shard 1
   ▼   ▼   ▼  (scatter)     ├── replicas of shard 2
  S1  S2 ... S2000          ├── ...
   │   │   │                └── replicas of shard 2000
   ▼   ▼   ▼  (each returns top-K local)
       │
       ▼ Mixer aggregates: takes top-K of K×N candidates
       │
       ▼
  Re-ranker (ML model with fancier features)
       │
       ▼
  Snippet generator → fetches doc text, builds preview
       │
       ▼
  Response
```

Each shard returns its top ~100 candidates. The mixer merges (K×N candidates), re-ranks the top ~1000, and returns top 10 to the user.

**Latency budget:**
- Parser: ~5 ms
- Scatter to shards: ~100 ms (slowest shard wins; tail-tolerance via replicas)
- Mixer + re-ranker: ~50 ms
- Snippet generation: ~50 ms
- Total: ~200–250 ms median

## 8. Tail latency: the killer

Median is easy. P99 is hard. With 2000 shards, even if each has 99.9% sub-100ms latency, the slowest of 2000 is the P99. Probability that *all* return fast = 0.999^2000 ≈ 13%.

**Fixes:**
- **Hedged requests**, send to 2 replicas per shard, take the first response. Costs 2× compute, drops P99 dramatically.
- **Replica hot-swapping**, if one replica is slow (GC pause, hardware glitch), quickly switch to a peer.
- **Chunked replies**, top-K from each shard streams back; mixer waits a deadline, takes whatever's arrived.

This is the same tail-tolerance problem from [Top-K / Trending](/blog/system-design/design-top-k-trending), Jeff Dean wrote the canonical paper on it ("The Tail at Scale").

## 9. Ranking: from string match to relevance

The classical IR formula:

**TF-IDF / BM25:**
- TF: how often the term appears in this doc.
- IDF: how rare the term is across the corpus (rare terms are more discriminating).
- BM25 normalizes for document length.

But by the 2010s, ranking became ML-driven:

### Modern ranking (very simplified)

```
Stage 1: candidate generation
  - Inverted index narrows 100B docs → ~50K candidates per query
  - BM25 + simple signals (PageRank, freshness)
  - Per-shard work; this is what posting lists feed

Stage 2: feature hydration
  - Top ~5K candidates: load hundreds of signals per doc
    (freshness, click-through history, page quality, anchor text...)

Stage 3: ML scoring
  - LambdaMART (gradient-boosted trees) or transformer ranker
  - Top ~500 candidates → final scores

Stage 4: re-ranking
  - Personalization (user history, location)
  - Diversity (don't return 10 nearly-identical results)
  - Top 10 → response
```

**Key insight:** ranking is a **funnel**. Cheap signals at the top to cull the candidate set; expensive signals at the bottom. Each stage cuts the candidate count by 10–100×.

## 10. PageRank (the original killer signal)

Pages are nodes; hyperlinks are edges. PageRank ≈ probability that a random surfer lands on each page.

Computed as a sparse matrix iteration over the whole web graph (offline batch job, weekly).

**By itself**, PageRank is a tiny part of modern Google ranking. But historically it's what set Google apart, it captured **authority** (a page linked to by NYT is more important than the same page linked to by some random blog).

## 11. Crawling integration

The [Web Crawler](/blog/system-design/design-web-crawler) post covers this in detail. Key integration points with search:
- Crawler emits `(url, content, fetched_at)` to a Kafka topic.
- **Indexer** subscribes; for each new/changed page:
  - Parse HTML → extract text, links, structured data.
  - Compute features (anchor text in/out, language, quality signals).
  - Update inverted index for this doc's shard.
- **Freshness tier**, news/breaking content goes through a hot-path indexer that updates the live index in seconds; bulk updates are batched.

## 12. Index updates: the freshness/throughput trade-off

You can't rebuild a 10 PB index per query update. Standard approach:

- **Static base index**, rebuilt every few days, contains the bulk of the corpus.
- **Delta indexes**, small, fast in-memory indexes containing recent changes.
- Query path: scatter to base + delta shards, merge results.
- Periodically, deltas are merged into the base.

This is the same "log-structured merge" idea behind LSM trees in databases like Cassandra and RocksDB.

## 13. Spelling correction & query understanding

Before reaching the index, the query is processed:
- **Tokenization**, split on whitespace, handle punctuation.
- **Spell correction**, `"berlin pizaa"` → `"berlin pizza"` using edit distance + query-log priors (popular query → likely correction).
- **Synonym expansion**, `"car"` includes `"automobile"`.
- **Language ID**, choose the right language stemmer.
- **Intent classification**, informational, navigational, transactional? Affects ranking weights.

## 14. Snippet generation

For each top-10 result, extract a 2-line preview:
- Find sentences in the doc containing the query terms.
- Highlight matched terms.
- This requires fetching the **forward index** (full doc text or processed form), a separate doc-store, also doc-sharded.

Snippet generation is its own latency budget (~50 ms), so the doc-store is heavily cached and indexed by doc ID.

## 15. Caching

- **Query result cache**, same query in last 60 sec returns cached top-10. ~30–40% of queries are repeats (lots of `"facebook"`, `"weather"`, etc).
- **Posting list cache**, common terms' posting lists in RAM.
- **Doc-store cache**, top-N most-clicked docs cached for snippet generation.

Caching saves enormous resources but invalidation is hard for personalized results, so cache is per-(query, language, locale, market), not personalized.

## 16. The trade-offs interviewers will probe

| Question | What they want to hear |
|---|---|
| "Term-sharded vs doc-sharded?" | Doc-sharded scales linearly; term-sharded has hot-shard problems |
| "Why scatter-gather to 2000 shards?" | Latency-parallel; tail-tolerance is the trick |
| "How does ranking work end-to-end?" | Funnel: BM25/PageRank → ML scoring → personalization |
| "How do you keep results fresh?" | Static base index + delta indexes (LSM-style) |
| "How does PageRank fit in?" | One signal among hundreds; offline batch over web graph |
| "What's the latency budget?" | 200–300 ms split across parser, scatter, mix, snippet |
| "How does spell correction work?" | Edit distance + query-log priors |

## 17. The 30-second summary

> Web search is **doc-sharded inverted index serving with scatter-gather query, ML-based ranking funnel, and continuous incremental indexing**. The crawler feeds new docs into shards via deltas; queries fan out to thousands of shards in parallel and the mixer aggregates top-K. Tail latency dominates, solved by hedged requests across replicas. Ranking went from BM25/PageRank to a multi-stage ML pipeline; PageRank is now one signal among hundreds.

Lead with the doc-sharded scatter-gather, show the funnel, name-drop tail-tolerance, and end on the freshness/static-base/delta architecture. That's the staff-level answer.
