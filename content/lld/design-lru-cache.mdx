LRU Cache is asked at Google, Meta, and Amazon — often as a warm-up before a harder design question. The combination of two data structures (`HashMap` + doubly linked list) for O(1) operations is the expected insight.

## 1. Clarify requirements

- Fixed capacity?
- Thread-safe?
- Eviction policy: strict LRU or approximate (like Java `LinkedHashMap`)?
- TTL (time-to-live) on entries?
- Generic types or string keys?

Agreed scope:

> Fixed capacity, strict LRU, thread-safe, generic key-value, no TTL.

## 2. Data structure insight

- **HashMap**: O(1) key → node lookup
- **Doubly linked list**: O(1) move-to-front and evict-from-back

```
HEAD ↔ [most recent] ↔ ... ↔ [least recent] ↔ TAIL
```

```java
public class LRUCache<K, V> {
  private final int capacity;
  private final Map<K, Node<K, V>> map;
  private final Node<K, V> head;   // dummy head
  private final Node<K, V> tail;   // dummy tail
  private final ReentrantReadWriteLock lock = new ReentrantReadWriteLock();

  public LRUCache(int capacity) {
    this.capacity = capacity;
    this.map = new HashMap<>(capacity);
    head = new Node<>(null, null);
    tail = new Node<>(null, null);
    head.next = tail;
    tail.prev = head;
  }

  public Optional<V> get(K key) {
    lock.readLock().lock();
    try {
      Node<K, V> node = map.get(key);
      if (node == null) return Optional.empty();
    } finally { lock.readLock().unlock(); }

    // Need write lock to move node to front
    lock.writeLock().lock();
    try {
      Node<K, V> node = map.get(key);
      if (node == null) return Optional.empty();
      moveToFront(node);
      return Optional.of(node.value);
    } finally { lock.writeLock().unlock(); }
  }

  public void put(K key, V value) {
    lock.writeLock().lock();
    try {
      if (map.containsKey(key)) {
        Node<K, V> node = map.get(key);
        node.value = value;
        moveToFront(node);
      } else {
        if (map.size() == capacity) evictLRU();
        Node<K, V> node = new Node<>(key, value);
        map.put(key, node);
        addToFront(node);
      }
    } finally { lock.writeLock().unlock(); }
  }

  private void moveToFront(Node<K, V> node) {
    remove(node);
    addToFront(node);
  }

  private void addToFront(Node<K, V> node) {
    node.next = head.next;
    node.prev = head;
    head.next.prev = node;
    head.next = node;
  }

  private void remove(Node<K, V> node) {
    node.prev.next = node.next;
    node.next.prev = node.prev;
  }

  private void evictLRU() {
    Node<K, V> lru = tail.prev;
    if (lru == head) return;  // empty cache
    remove(lru);
    map.remove(lru.key);
  }

  private static class Node<K, V> {
    K key; V value;
    Node<K, V> prev, next;
    Node(K k, V v) { key = k; value = v; }
  }
}
```

## 3. Why dummy head and tail?

Dummy sentinel nodes eliminate null checks in `addToFront` and `remove`. Without them, every boundary operation needs `if (prev != null)` guards. It's a small detail that shows polish.

## 4. Thread safety analysis

| Approach | Trade-off |
|---|---|
| `synchronized` on all methods | Simple, but serialises reads unnecessarily |
| `ReentrantReadWriteLock` | Reads concurrent, writes exclusive — but `get` still needs write lock (it mutates order) |
| `ConcurrentHashMap` + lock-striping | Complex; hard to maintain LRU ordering correctly |
| Approximate LRU (`ConcurrentLinkedQueue`) | Relaxed ordering — used in Caffeine cache |

In an interview, `ReentrantReadWriteLock` is the right answer. Mention that production caches (Caffeine) use approximate LRU to avoid write-lock contention on reads.

## 5. LRU with TTL (follow-up)

Add an `expiresAt: Instant` field to `Node`. On `get`, check if `Instant.now().isAfter(expiresAt)` — if so, remove and return empty. Run a background thread to periodically evict expired entries.

## 6. Extending to different eviction policies

```java
public interface EvictionPolicy<K, V> {
  void onAccess(K key);
  void onPut(K key, V value);
  K evict();
}
```

Implement `LRUPolicy`, `LFUPolicy`, `FIFOPolicy` — inject into a generic `Cache<K, V>` context. This is the Strategy pattern again.

## 7. Follow-ups

| Follow-up | Answer |
|---|---|
| LFU (Least Frequently Used) | Map of frequency → doubly linked list; on access, move to higher-freq bucket. |
| Distributed LRU | Redis `ZSET` with score = access timestamp; evict lowest score. |
| Size-based eviction (not count) | Each entry has a `weight`; evict when total weight exceeds max. |
| Persistence | Write-through: write to DB on every `put`. Write-back: flush dirty entries periodically. |

## 8. The 30-second summary

> HashMap gives O(1) lookup; doubly linked list gives O(1) eviction and promotion. Dummy sentinels remove boundary checks. `ReentrantReadWriteLock` protects concurrent access — but note that even `get` needs a write lock because it reorders the list. Production caches use approximate LRU to avoid this bottleneck.
